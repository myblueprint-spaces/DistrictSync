# Machine scope and the profile location

Developer reference for where DistrictSync keeps its profile — the per-user app-data dir, the `DISTRICTSYNC_DATA_DIR` support/test override, and plan 0049's machine scope (`C:\ProgramData\DistrictSync`: the HKLM switch, the trust checks, provisioning, the unelevated handover, the honest predicates, the principal model and gMSA) — plus the `--diagnose` support report. Every section below was moved **verbatim** from `CLAUDE.md` by plan 0053 S15 (2026-09-30): what was one long paragraph there is split into sections at its bold-led spans, with headings added and no words changed (the change list is in `.claude/plans/0053-s15-disposition-map.md` (deleted in DSYNC-18; in git history)). The rules stay in `CLAUDE.md` (**Commands → SFTP credential setup** and **Subsystem guides → Machine scope**). The scheduled task itself — COM registration, `task_com.Principal`, per-operation elevation — is in [scheduler.md](scheduler.md).

## The profile location and `DISTRICTSYNC_DATA_DIR`

**`DISTRICTSYNC_DATA_DIR`** (support/test seam) overrides that whole profile location — step 0 of `user_data_dir()`, **wins outright** (no legacy fallback; blank = unset; a **relative** value is REFUSED with `ValueError`; an unusable dir raises `RuntimeError` rather than silently falling back). `migrate_legacy_data_dir()` no-ops while it points ELSEWHERE — an override aimed AT the platform dir must not strand `~/.districtsync`. It exists because **on Windows** `platformdirs` ignores a `LOCALAPPDATA` env var (`SHGetKnownFolderPath`), so a **frozen exe** has no other SUPPORTED redirect there (Linux still honors `XDG_DATA_HOME`; macOS has no equivalent). It is NOT the only one that works, and that correction is security-relevant: **MEASURED on platformdirs 4.9.6 (`windows.py:356-361`), `WIN_PD_OVERRIDE_<CSIDL>` is consulted BEFORE `SHGetKnownFolderPath`** — an unprivileged env var. `machine_data_dir()` therefore REFUSES (`MachineScopeRefused(REDIRECTED)`) while any `WIN_PD_OVERRIDE_*` is set, since that variable would otherwise redirect the very directory provisioning owns, ACLs, seals a LocalMachine secret into and commits HKLM against — used by the CI exe smokes and the fresh-profile QA walk. The startup banner logs the resolved dir. **Never run the app/CLI locally without it** (or a monkeypatched seam) — a bare run writes into the real profile's `etl_tool.log` + `history.db`.

## The machine-scope ladder and its trust checks

**Machine scope (plan 0049, REACHABLE since S-2b — the Schedule press provisions):** the ladder now runs override → **HKLM switch** (`SOFTWARE\DistrictSync\MachineScope`, REG_DWORD 1, opened with the exported `MACHINE_SCOPE_KEY_ACCESS` = `KEY_READ | KEY_WOW64_64KEY` — a 32-bit-view read/write would answer about a different key) → per-user. With the switch ON, `machine_data_dir()` (`C:\ProgramData\DistrictSync`) must pass `_assert_machine_dir_trusted` — exists · not a reparse point · owner SID ∈ {Administrators, SYSTEM} (SID **strings**, never localised names) · `SE_DACL_PROTECTED` — or the whole resolution **RAISES** `MachineScopeRefused(reason)` (`StrEnum`: `SWITCH_UNREADABLE·MISSING·NOT_A_DIRECTORY·REPARSE·FOREIGN_OWNER·INHERITED_ACL·INACCESSIBLE·OPEN_ACE·REDIRECTED·RUNS_UNWRITABLE`; `launcher._MACHINE_SCOPE_CAUSES` must carry one plain-language cause per member — a completeness test, so a new reason without copy is RED).

**`OPEN_ACE` (S-1b-i)** is the explicit open-group ace walk (`assert_no_open_aces` over `OPEN_GROUP_SIDS` = Everyone/Authenticated Users/Users, **ALLOW aces only** — a DENY ace for Everyone is hardening, and refusing it would invert the check): `SE_DACL_PROTECTED` proves inheritance was stripped, NOT that the DACL is closed.

**It NEVER falls through to the per-user profile** — that fallback is the split-brain the whole plan exists to remove — and an unreadable switch REFUSES too (only a `FileNotFoundError` means off). Path and scope are decided together and **pinned once per process** (`pin_data_dir()` at both entry points before the log sink opens; `is_machine_scope()` is the ONE predicate; `reset_data_dir_pin()` for tests). The override is **never** machine scope. `handshake_dir()` is the per-user, **non-creating** location in EVERY scope (the elevation handshake must not follow the profile into a directory another principal can write, and `sweep_orphans` runs unconditionally at both entry points — it returns 0 rather than materialising a second profile). On machine scope only, `user_log_file()`/`user_history_db()` move under `runs/` with a per-writer log name (`accounts.sanitise_account_for_filename`). DPAPI goes through `utils/dpapi.dpapi_call(..., *, flags)` — `flags` is **required** (a round trip passes with the wrong scope; `elevation` stays CurrentUser + `UI_FORBIDDEN`).

## One secret store: the SELECT RULE

**The SELECT RULE (S-1a-ii):** `sftp/secret_store.select_store()` returns `MachineSecretStore()` iff `is_machine_scope()`, else `UserSecretStore()` — **never both, never a fallback chain** (that would restore the split-brain), and always the keyring under `DISTRICTSYNC_DATA_DIR` by construction of the pin; the same predicate adds `has_secret` as a machine-scope-only conjunct of `sftp_is_configured()` (per-user byte-identical) (the scheduled nightly once staged its delivery zip in `runs/tmp`; since DSYNC-57 the conversion writes the zip into the output folder and delivery uploads that file, so nothing is staged and `pipeline._delivery_staging_dir` is gone). Every run record carries `run_as` (`accounts.process_account()`, set in `build_run_record` so both sinks share it) — a record KEY, **no `user_version` bump**.

## Provisioning (the elevated half)

**PROVISIONING (S-1b-i, `src/scheduler/provisioning.py`, INERT — nothing calls it until S-2):** three `elevated_apply` ops behind ONE UAC prompt — `provision` · `grant_current_user` · `prune_principal`. The directory is created **WITH its DACL in one `CreateDirectoryW`** (SDDL via `ConvertStringSecurityDescriptorToSecurityDescriptorW` + `SECURITY_ATTRIBUTES`), because the plan's original strip-then-verify sequence was MEASURED impossible (`icacls /inheritance:r` leaves a **zero-ACE** DACL → `iterdir` AND `rmtree` both raise `WinError 5`, so neither the anti-plant check nor the rollback can run). `ERROR_ALREADY_EXISTS` is the **atomic never-adopt gate**. SID strings only (`O:BA`, `SY`/`BA`, else `LookupAccountNameW`) — a localised `Administrators` fails on a German Windows. Principal gets **RX at the root, M on `runs/` only**. Step 6 verifies with `assert_machine_dir_trusted` + the ace walk + `history_db_in()` — **never an icacls exit code**; step 7 commits HKLM with the imported `MACHINE_SCOPE_KEY_ACCESS | KEY_WRITE` (a 32-bit-view write commits `WOW6432Node` and reports success). Pre-commit failure → rmtree what THIS call created (`if created` — a RESUME must never delete the directory holding the already-sealed secret) and a removal failure gets its own step id.

**Resume rule:** trusted ⇒ re-run 3b–8 idempotently; `migrate_profile` SKIPS what is already at the destination, which is what keeps a stale per-user `config.json` from overwriting the shared one. Refuses under `DISTRICTSYNC_DATA_DIR` in BOTH halves and on a parent/child source-path disagreement. Every `icacls` non-zero exit is **FATAL** here (the deliberate inverse of `elevation._set_owner_only_dacl`'s warn-and-continue: there DPAPI is the boundary, here the DACL is). Result vocabulary = a `ProvisionStep` id + the icacls exit code, never stderr/paths/either secret. AC1's old "no registry write API under `src/`" pin MOVED: the narrower pin is that `provisioning.py` is the ONLY registry writer and uses the exported mask.

**A READER NEVER CREATES A PROFILE SUBFOLDER (DSYNC-110).** Under the root the principal holds RX only, so a mkdir on the nightly's read path is `[WinError 5] Access is denied` and fails the run. `paths.user_mappings_dir()` is a PURE path (a missing `mappings/` = no user mappings; the loader's search and `available_configs` already skip it); the ONE creator is `paths.ensure_user_mappings_dir()`, called by `authoring.write_overlay` after the load-back passes. Provisioning deliberately does NOT pre-create `mappings/`: `migrate_profile` skips any destination that already exists, so an empty folder made in step 3 would silently drop the admin's per-user overlays at step 4 — and an admin-created `mappings/` inherits the root's RX for the principal anyway.

**EVERY PROTECTED FOLDER IS ONE TABLE (DSYNC-117).** `provisioning.PROTECTED_SUBTREES` lists each folder provisioning creates with a protected descriptor, and what the setup administrator and the nightly's principal get on it:

| Folder | Setup administrator (and every administrator granted later) | Nightly principal |
|---|---|---|
| root (`C:\ProgramData\DistrictSync`) | `M` | `RX` |
| `runs\` | `M` | `M` |

(SYSTEM and Administrators have `F` on both; both are `D:P`, inheritance off.) The descriptors (`_subtree_sddl`), step 3 (`_create_profile`) and `grant_current_user` read the table, so a new protected folder cannot be created without the grant reaching it. Before the table, `grant_current_user` added one `(OI)(CI)M` ace to the root only, and since `runs\` is protected that ace never reached it: the granted administrator's filtered token (where `BUILTIN\Administrators` does not apply) could open the profile but not create `runs\etl_tool-interactive-<tag>.log`, and the lab saw PyInstaller's traceback dialog (`[Errno 13]`). The grant now gives the setup administrator's right on every row that exists (a missing `runs\` is skipped; only `provision`'s resume can re-create it with its descriptor); `icacls /grant` merges into an existing explicit ace, so it is idempotent, and on an install granted by an earlier build it adds exactly the missing `runs\` ace. This is every build that provisions, not just the MSI: the one-file `DistrictSync-windows.exe` provisions the same way from Setup's Schedule press (since 0049 S-2b), so its shared profiles have the same protected `runs\` and the same root-only grants, and the same code repairs them. Still open, for DSYNC-115: `_ensure_runs_and_principal`'s principal grant and `apply_prune_principal`'s loop spell the folder list themselves and should iterate the table.

**THE REPAIR IS RE-OFFERED BY A PROBE (DSYNC-117).** An administrator granted by an earlier build passes the trust checks (the root ace exists), so no refusal would ever bring the grant window back. The window's boot therefore runs `paths.assert_runs_writable()` right after `pin_data_dir()` (`launcher.boot_profile`): on machine scope only, it creates and removes one `.write-probe-<random>` file in `runs\` with ONE `os.open(O_CREAT|O_EXCL)` and no retry (a real create; `os.access` on Windows never reads the DACL, which is also why `tempfile.mkstemp` cannot be used: it retries a denied create while `os.access` says writable, up to TMP_MAX, and hung the launch). Only an access denial (`PermissionError` with `winerror` 5 or none) raises `MachineScopeRefused(RUNS_UNWRITABLE)`; any other failure (disk full, antivirus, sharing violation) is logged by type and errno and the boot carries on, the log sink's fallback covering the log. `RUNS_UNWRITABLE`'s dialog copy (`format_user_error`) names the handshake log and says the nightly is unaffected. The refusal is one `grant_access` treats as grantable, so the next open shows the grant window and the grant now covers `runs\`. A missing `runs\` is `MISSING` (not grantable). The probe is the WINDOW's only: the CLI and the nightly are never refused for it (the nightly's principal holds `M` on `runs\` by descriptor).

**A LOG FILE THAT CANNOT BE OPENED NEVER KILLS THE APP (DSYNC-117).** `logger.get_logger` builds the rotating file handler through `_open_file_sink`; an `OSError` (incl. `PermissionError`) falls back to `<handshake_dir()>\etl_tool.log` (the declared per-user exception, created if absent, exactly as `_report_machine_scope_refusal` does), else to stderr, and logs ONE line (`FALLBACK_NOTICE`: the error type and errno, never `str(exc)`, a path or an account). It never resolves `user_data_dir()`, so it cannot fall through to the per-user PROFILE. Both entry points use it (`main._configure_cli_logging`, `launcher.boot_logging`); `launcher._write_traceback` falls back to the same folder. (The lab's traceback came through the CLI because the old `os.execv` relaunch split `C:\Program Files\...` into two arguments; DSYNC-114's `ui_flet/relaunch.py` fixed that. The fallback covers both entry points regardless.)

## The parent (unelevated) half

**THE PARENT (unelevated) HALF (S-1b-ii, `src/scheduler/provision_session.py`):** `complete_handover(*, persist, reenter)` gates on the parent's OWN `paths.machine_switch_on()` re-read — **never the child's claim**, which is absent on exactly the outcomes (TIMEOUT, no result) where it may nonetheless have committed — and there is deliberately no outcome parameter to gate on instead. Then re-pin → **assert `is_machine_scope()` before anything destructive** → re-point the sink → set the per-user `config.json`/`history.db`(+`-wal`/`-shm`) aside as `*.pre-machine-<ts>` → `MOVED.txt` → `persist` → `reenter`: the callback ORDER is the spec's ordering rule made structural (the three-facet save must land in the MACHINE config, and re-entry must follow it).

**The `MOVED.txt` FENCE (amendment 2)** is what makes the rename mean anything: `AppConfig.save()` raises `SettingsOverwriteRefused` and `write_run_record` WARNs + returns `False` when `paths.profile_superseded()` sees the breadcrumb (checked at the profile ROOT — the store sits under `runs/` on machine scope), because `load()` maps `FileNotFoundError` to defaults with no log and both writers recreate silently.

**The auto-grant window (amendment 3)** is PRE-SHELL (`ui_flet/grant_window.py` + the pure `grant_access.py`), rendered from `launcher.main`'s refusal path — the shell mount point does not exist at the moment of failure — branching on the TYPED reason (only `INACCESSIBLE` and, since DSYNC-117, `RUNS_UNWRITABLE` are grantable), re-launching on success through the shared `ui_flet/relaunch.py` (close the window, quoted list spawn, exit — DSYNC-114), and saying UP FRONT that over-the-shoulder consent fails closed (the handshake is DPAPI CurrentUser → `DSYNC_DIFFERENT_ACCOUNT`).

## Honest predicates (S-2a)

**A machine-wide install refuses a per-user profile (plan 0055 M2b, DSYNC-106):** `scheduler/machine_setup.needs_machine_setup()` is TRUE only for `install_kind() is MACHINE` with the switch PROVABLY off (`switch_state() is False`) and no `DISTRICTSYNC_DATA_DIR`; an unreadable switch or any surprise reads FALSE (the existing refusal handles an unreadable switch). Then the window shows only the first-run step (`ui_flet/machine_setup_window.py`) and the CLI refuses everything but `--machine-setup`/`--version`/`--help` (`machine_setup.NOT_SET_UP_CLI`, exit 1), both decided BEFORE `migrate_legacy_data_dir`/`pin_data_dir`/the log sink. `--machine-setup` and the window share ONE ladder and copy table (`machine_setup.run`, moved out of `main.py`); the delivery seed is read from the per-user `config.json` without pinning (`machine_setup.delivery_seed`). The declared exception: the UAC handshake files and `MOVED.txt` live in `handshake_dir()` (= the per-user profile folder).

**`--diagnose`'s Installation block (plan 0055 D2, DSYNC-102):** `src/utils/installation.py` (read-only, total) + `diagnostics._installation_lines`: install folder, running version vs the MSI product's version (they differ after a Velopack apply: run the newest MSI only), whether a copy installed for one account is also present, the SYSTEM updater's folder (absent / trusted / others can change it) and its last `updater.log` line, the last update check and how far behind this copy is (those two skipped before machine setup). Pinned by `tests/test_diagnose_installation.py`.

**No names (plan 0055 N1, DSYNC-100):** nothing the app writes names an account. `src/utils/account_tag.py`: `account_tag(account) = HMAC-SHA256(key, casefolded account)[:12]`; the key is the computer's own `MachineGuid` (`HKLM\SOFTWARE\Microsoft\Cryptography`, readable by every account), so per-user and shared profiles on one computer tag an account identically (machine setup's copied `history.db` keeps "this account"; a 0049 install has tags at once) and a copied log cannot be reversed off the computer; off Windows, an exclusively-created `<profile>\account-tag.key`. `provisioning._commit_machine_switch` DELETES a 0049 `ProvisionedBy` (an install not re-provisioned keeps that value; `--diagnose` no longer prints it). Records carry `run_as_tag` (Run History compares tags; an older record's `run_as` is still read, never written); the machine-scope log is `runs\etl_tool-<scheduled|interactive>-<tag>.log` (role from an argv pre-scan, `account_tag.process_role`; an unreadable key → `nokey`, never a reversible hash); the schedule-check marker carries the tag. Every log FILE line, tracebacks included, goes through `src/utils/redact.py` (`RedactingFormatter`: any home folder under `Users`/`Profiles`/`home`/`homes`/`UserData` on a drive, a UNC share or POSIX → `<user>`; this account, any case → `<account>`; a name that is not in such a folder or this account is NOT caught — the writers stopped writing names instead). The Home/Settings line says "set up by an administrator". `--diagnose` prints the tag and the principal KIND. Pinned by `tests/test_no_names_in_logs.py` (its scan runs a scheduled pipeline as a distinctively named account). `AppConfig.schedule_run_as_user` keeps the account (needed to re-register; config, not a log).

**S-2a (honest predicates):** `shared_records: bool` is REQUIRED keyword-only on `probe_schedule`/`derive_schedule_status`/`sync_window_paused`, sourced from `is_machine_scope()` at all five view call sites, and the ONE rule everywhere is **suppress only when `foreign_account and not shared_records`** — Slice C (0046) made "the records land elsewhere" true by suppressing alarms; machine scope makes it FALSE. `FOREIGN_RECORDS_SHARED_NOTE` says records appear "from now on" (migration copies the ADMIN's `history.db`; the service account's own profile is never touched, so a pre-provisioning gap is real and permanent); `SYNC_WINDOW_SHARED_NOTE` makes a POSITIVE claim so it takes the schedule state and fires on CONFIRMED-LIVE only. `delivery_password_line` has four forms — form 2 (per-user) byte-identical, form 3's "no nightly is scheduled" on **MISSING only** (an UNKNOWN read-back is not an absence), form 1 with an account-less variant since `schedule_run_as_user` is `""` by contract when scheduling as the signed-in account. `home_status.machine_scope_line` is `None` on every per-user install (absent, not qualified) and `MACHINE_SCOPE_LINE_LEAD` + `diagnostics.SCOPE_SHARED`/`SCOPE_PER_USER` are single-sourced because the partner docs quote them to decide whether the manual `--sftp-configure` step is still needed — **and the wrong answer there is SILENT** (`tests/test_partner_doc_schedule_copy_parity.py` pins all three; three docs wrapped the phrase mid-line before the pin existed). `run_history.run_as_display` reduces the record's `run_as` to a bounded two-member vocabulary via `principal_key` — never a raw `DOMAIN\user` — and `components.run_table` renders the column only when values VARY (`""` is not a distinct value, so an upgraded ledger does not conjure it).

## The flow (S-2b)

**S-2b (the flow):** `RegisterBlock.DELIVERY_SECRET_UNREADABLE` is the ONE pre-UAC gate, ANDed with foreign-ness INSIDE `register_block` and read through `select_store()` (never "the keyring" by name — on a second provisioning the secret is already in the machine store); `FOLDER_NOT_SHAREABLE` is deliberately NOT a member (a confirm-level warning over `src/utils/unc.py` instead — the predicate is wrong in both directions and says so; DECISIONS 2026-09-18). `complete_handover` runs on EVERY outcome incl. a killed child, `persist` is bound to SUCCESS alone (a declined UAC must not record a nightly that does not exist), `refused` is TERMINAL and freezes Setup (the pin is left unset, so the next click can only crash), and switch-committed \u2227 register-failed LEADS with the scope change. `ui_flet/handover_result.py` is a process-scoped one-shot (`take()` reads AND clears) drained **once per Home mount, outside `_render`** and rendered ABOVE the verdict band — a deliberate one-paint exception to verdict-first. `setup_errors.classify_provision_step` is separate from `classify_schedule_error` because `ProvisionRefused.message` interpolates the step + icacls exit + a rollback clause and could never match an exact-equality branch; its completeness test closes a real hole, since the existing reflection sweep scans only `task_com`/`windows`/`elevated_apply`. `ReconcileOutcome.BLOCKED_DELIVERY_SECRET` exists because `BLOCKED_ACCOUNT`'s copy says "check the Windows account and its password" — a misdirect one field over from `BLOCKED`'s "fix the run time".

## The principal model (S-3) and gMSA (S-4)

**S-3 (the principal model):** `RegisterParams.kind: PrincipalKind` REPLACES the `password is not None` inference (deleted, not wrapped — `apply_definition` now has ONE `RegisterTaskDefinition` call and no branch); MSA uses `TASK_LOGON_PASSWORD`, **not** `TASK_LOGON_SERVICE_ACCOUNT` (with a domain `UserId` the `<LogonType>` element is silently dropped from the serialized XML), and `TASK_LOGON_S4U` stays undefined. Five states unrepresentable in `__post_init__`. `_do_register`'s ladder is kind-aware and `_do_provision` SHARES the callable — the make-or-break, because it validated unconditionally against a regex with no `$` and every foreign-principal register goes through elevation. `CronScheduler` refuses on the KIND (its old `password is not None` guard let an MSA through into a cron line with no account). `ScheduleReadback` gains `run_as`/`logon_type` for DISPLAY with a fail-open WARNING on mismatch; `foreign_task_account` still reads the RECORD.

**S-4 (gMSA, Settings only):** the disclosure sits behind `_build_schedule_section(allow_gmsa=False)` — the FIRST wizard/Settings fork in that function — and `schedule_run_as_kind` is the FOURTH atomic facet; `principal_kind_from_record` is the ONE spelling of the absent-value rule (stored wins, else `PASSWORD` iff a user is recorded) and can **never** return `MANAGED_SERVICE_ACCOUNT`, because sniffing the `$` off a name is the inference S-3 just deleted. BOTH gate rungs dispatch on kind (`ACCOUNT_SHAPE` ran `validate_run_as_user` unconditionally and refused every gMSA first, for the wrong reason). Errors FORK rather than multiply — no new canonical, since the gMSA taxonomy is unmeasured. **The "not yet tested against a live domain" hedging is GONE (owner decision 2026-09-21, reversing 2026-09-18's honesty constraint — shipping to SD60 as a supported option, and a second download just to delete a caption is partner friction).** `GMSA_UNTESTED_CAPTION` is deleted, not stubbed. What survived the removal is the OPERATIONAL content and is pinned: the MSA arm still shows `0x80070534` via `_code` and still offers NO "try again" (retrying a name the directory does not know changes nothing); `GMSA_PREREQUISITES` still renders on all three surfaces; and both partner docs + the CHANGELOG still state that provisioning runs BEFORE registration, so a failed gMSA register leaves the machine-scope switch COMMITTED and this version cannot undo it (`test_the_unshareable_consequence_survives_in_both_docs` replaced the retired hedge row — that consequence, not the hedge, is what a district cannot discover by trying). The failure taxonomy is still unmeasured, so a new gMSA failure gets a FORK + the `[HRESULT ` log anchor, never an invented canonical.

## The named hole

**THE NAMED HOLE (narrowed by DSYNC-33):** `prune_principal` had a handler and an implementation but no producer in `src/`. Since DSYNC-33 Setup's Remove produces it for a recorded MANAGED_SERVICE_ACCOUNT principal on a machine-scoped install (`provision_session.request_removal_with_revoke` — one prompt; the child deletes, confirms MISSING, then prunes). The unconfirmed-delete case is decided: the child prunes NOTHING (`ProvisionStep.DELETE`) and the parent resolves the removal by its own read-back; a refusal before the delete falls back to the plain remove. A retired PASSWORD principal is still removed with `{"op": "delete"}` and keeps its aces (open backlog item). The flow and its guarantees: [scheduler.md](scheduler.md#the-schedule-check-proving-the-nightly-can-start-dsync-33).

## Machine setup without a nightly (plan 0055 M2a, DSYNC-95)

`DistrictSync.exe --machine-setup [--updates off|notify|on]` provisions the shared profile with NO nightly task, for the
machine-wide MSI (Velopack's MSI cannot ask questions, so setup happens after the install). It is the `provision` op with
a blank principal (the setup administrator is the only one granted anything; a nightly for another account grants that
account when it is scheduled) and a register step that does nothing: `provisioning.build_machine_setup_payload` (refuses
under `DISTRICTSYNC_DATA_DIR`, and an unknown mode, before any prompt) → the elevated child's `_do_machine_setup`
(validates before `apply_machine_setup`, so a bad request never switches the computer) → `apply_provision(...,
update_mode=)`. The update mode (`src/update/policy.py`; default `notify`, owner decision O1) is written as `UpdateMode`
(REG_SZ) by `_commit_machine_switch` in the same commit, BEFORE `MachineScope`; the schedule-time provision passes `None`
and leaves it. Re-running it, as the administrator who set the computer up, is the resume path, which is how the mode is changed later (any other account is refused earlier, at the profile pin). A re-run exits 0 only when the elevated child reports it completed: on a computer already set up the switch is on either way, so a declined prompt exits 1 and claims no mode. The
parent runs unelevated, as the window does: `provision_session.request_machine_setup` (shares `_elevate_and_read` with
`request_provision`) and then `complete_handover` on EVERY outcome, whose own switch read decides the exit code (0 only
when this session now uses the shared profile). A per-user installed copy is refused before any prompt. Reading the mode,
and the Group Policy key that overrides it, is U1; the first-run window step is M2b (DSYNC-106).

## `--diagnose` — the support report (plan 0049 D7)

`python -m src.main --diagnose` prints the read-only support report (plan 0049 D7) — recognised in the **argv pre-check beside `--elevated-apply`**, because `_cli` pins the data dir and RETURNS a machine-scope refusal before argparse exists; it keeps ONLY the console attach from the preamble, guards every profile-resolving line on its own, and always exits 0. It carries no passwords but is **not PII-free** (Windows accounts, folders, the SFTP username) and its header says so.
