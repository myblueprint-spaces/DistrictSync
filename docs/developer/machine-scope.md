# Machine scope and the profile location

Developer reference for where DistrictSync keeps its profile — the per-user app-data dir, the `DISTRICTSYNC_DATA_DIR` support/test override, and plan 0049's machine scope (`C:\ProgramData\DistrictSync`: the HKLM switch, the trust checks, provisioning, the unelevated handover, the honest predicates, the principal model and gMSA) — plus the `--diagnose` support report. Every section below was moved **verbatim** from `CLAUDE.md` by plan 0053 S15 (2026-09-30): what was one long paragraph there is split into sections at its bold-led spans, with headings added and no words changed (the change list is in `.claude/plans/0053-s15-disposition-map.md`). The rules stay in `CLAUDE.md` (**Commands → SFTP credential setup** and **Subsystem guides → Machine scope**). The scheduled task itself — COM registration, `task_com.Principal`, per-operation elevation — is in [scheduler.md](scheduler.md).

## The profile location and `DISTRICTSYNC_DATA_DIR`

**`DISTRICTSYNC_DATA_DIR`** (support/test seam) overrides that whole profile location — step 0 of `user_data_dir()`, **wins outright** (no legacy fallback; blank = unset; a **relative** value is REFUSED with `ValueError`; an unusable dir raises `RuntimeError` rather than silently falling back). `migrate_legacy_data_dir()` no-ops while it points ELSEWHERE — an override aimed AT the platform dir must not strand `~/.districtsync`. It exists because **on Windows** `platformdirs` ignores a `LOCALAPPDATA` env var (`SHGetKnownFolderPath`), so a **frozen exe** has no other SUPPORTED redirect there (Linux still honors `XDG_DATA_HOME`; macOS has no equivalent). It is NOT the only one that works, and that correction is security-relevant: **MEASURED on platformdirs 4.9.6 (`windows.py:356-361`), `WIN_PD_OVERRIDE_<CSIDL>` is consulted BEFORE `SHGetKnownFolderPath`** — an unprivileged env var. `machine_data_dir()` therefore REFUSES (`MachineScopeRefused(REDIRECTED)`) while any `WIN_PD_OVERRIDE_*` is set, since that variable would otherwise redirect the very directory provisioning owns, ACLs, seals a LocalMachine secret into and commits HKLM against — used by the CI exe smokes and the fresh-profile QA walk. The startup banner logs the resolved dir. **Never run the app/CLI locally without it** (or a monkeypatched seam) — a bare run writes into the real profile's `etl_tool.log` + `history.db`.

## The machine-scope ladder and its trust checks

**Machine scope (plan 0049, REACHABLE since S-2b — the Schedule press provisions):** the ladder now runs override → **HKLM switch** (`SOFTWARE\DistrictSync\MachineScope`, REG_DWORD 1, opened with the exported `MACHINE_SCOPE_KEY_ACCESS` = `KEY_READ | KEY_WOW64_64KEY` — a 32-bit-view read/write would answer about a different key) → per-user. With the switch ON, `machine_data_dir()` (`C:\ProgramData\DistrictSync`) must pass `_assert_machine_dir_trusted` — exists · not a reparse point · owner SID ∈ {Administrators, SYSTEM} (SID **strings**, never localised names) · `SE_DACL_PROTECTED` — or the whole resolution **RAISES** `MachineScopeRefused(reason)` (`StrEnum`: `SWITCH_UNREADABLE·MISSING·NOT_A_DIRECTORY·REPARSE·FOREIGN_OWNER·INHERITED_ACL·INACCESSIBLE·OPEN_ACE·REDIRECTED`; `launcher._MACHINE_SCOPE_CAUSES` must carry one plain-language cause per member — a completeness test, so a new reason without copy is RED).

**`OPEN_ACE` (S-1b-i)** is the explicit open-group ace walk (`assert_no_open_aces` over `OPEN_GROUP_SIDS` = Everyone/Authenticated Users/Users, **ALLOW aces only** — a DENY ace for Everyone is hardening, and refusing it would invert the check): `SE_DACL_PROTECTED` proves inheritance was stripped, NOT that the DACL is closed.

**It NEVER falls through to the per-user profile** — that fallback is the split-brain the whole plan exists to remove — and an unreadable switch REFUSES too (only a `FileNotFoundError` means off). Path and scope are decided together and **pinned once per process** (`pin_data_dir()` at both entry points before the log sink opens; `is_machine_scope()` is the ONE predicate; `reset_data_dir_pin()` for tests). The override is **never** machine scope. `handshake_dir()` is the per-user, **non-creating** location in EVERY scope (the elevation handshake must not follow the profile into a directory another principal can write, and `sweep_orphans` runs unconditionally at both entry points — it returns 0 rather than materialising a second profile). On machine scope only, `user_log_file()`/`user_history_db()` move under `runs/` with a per-writer log name (`accounts.sanitise_account_for_filename`). DPAPI goes through `utils/dpapi.dpapi_call(..., *, flags)` — `flags` is **required** (a round trip passes with the wrong scope; `elevation` stays CurrentUser + `UI_FORBIDDEN`).

## One secret store: the SELECT RULE

**The SELECT RULE (S-1a-ii):** `sftp/secret_store.select_store()` returns `MachineSecretStore()` iff `is_machine_scope()`, else `UserSecretStore()` — **never both, never a fallback chain** (that would restore the split-brain), and always the keyring under `DISTRICTSYNC_DATA_DIR` by construction of the pin; the same predicate adds `has_secret` as a machine-scope-only conjunct of `sftp_is_configured()` (per-user byte-identical) and routes the scheduled nightly's zip staging to `runs/tmp` (`pipeline._delivery_staging_dir` — machine scope **and** `source == "scheduled"`; manual/CLI keep `%TEMP%`). Every run record carries `run_as` (`accounts.process_account()`, set in `build_run_record` so both sinks share it) — a record KEY, **no `user_version` bump**.

## Provisioning (the elevated half)

**PROVISIONING (S-1b-i, `src/scheduler/provisioning.py`, INERT — nothing calls it until S-2):** three `elevated_apply` ops behind ONE UAC prompt — `provision` · `grant_current_user` · `prune_principal`. The directory is created **WITH its DACL in one `CreateDirectoryW`** (SDDL via `ConvertStringSecurityDescriptorToSecurityDescriptorW` + `SECURITY_ATTRIBUTES`), because the plan's original strip-then-verify sequence was MEASURED impossible (`icacls /inheritance:r` leaves a **zero-ACE** DACL → `iterdir` AND `rmtree` both raise `WinError 5`, so neither the anti-plant check nor the rollback can run). `ERROR_ALREADY_EXISTS` is the **atomic never-adopt gate**. SID strings only (`O:BA`, `SY`/`BA`, else `LookupAccountNameW`) — a localised `Administrators` fails on a German Windows. Principal gets **RX at the root, M on `runs/` only**. Step 6 verifies with `assert_machine_dir_trusted` + the ace walk + `history_db_in()` — **never an icacls exit code**; step 7 commits HKLM with the imported `MACHINE_SCOPE_KEY_ACCESS | KEY_WRITE` (a 32-bit-view write commits `WOW6432Node` and reports success). Pre-commit failure → rmtree what THIS call created (`if created` — a RESUME must never delete the directory holding the already-sealed secret) and a removal failure gets its own step id.

**Resume rule:** trusted ⇒ re-run 3b–8 idempotently; `migrate_profile` SKIPS what is already at the destination, which is what keeps a stale per-user `config.json` from overwriting the shared one. Refuses under `DISTRICTSYNC_DATA_DIR` in BOTH halves and on a parent/child source-path disagreement. Every `icacls` non-zero exit is **FATAL** here (the deliberate inverse of `elevation._set_owner_only_dacl`'s warn-and-continue: there DPAPI is the boundary, here the DACL is). Result vocabulary = a `ProvisionStep` id + the icacls exit code, never stderr/paths/either secret. AC1's old "no registry write API under `src/`" pin MOVED: the narrower pin is that `provisioning.py` is the ONLY registry writer and uses the exported mask.

## The parent (unelevated) half

**THE PARENT (unelevated) HALF (S-1b-ii, `src/scheduler/provision_session.py`):** `complete_handover(*, persist, reenter)` gates on the parent's OWN `paths.machine_switch_on()` re-read — **never the child's claim**, which is absent on exactly the outcomes (TIMEOUT, no result) where it may nonetheless have committed — and there is deliberately no outcome parameter to gate on instead. Then re-pin → **assert `is_machine_scope()` before anything destructive** → re-point the sink → set the per-user `config.json`/`history.db`(+`-wal`/`-shm`) aside as `*.pre-machine-<ts>` → `MOVED.txt` → `persist` → `reenter`: the callback ORDER is the spec's ordering rule made structural (the three-facet save must land in the MACHINE config, and re-entry must follow it).

**The `MOVED.txt` FENCE (amendment 2)** is what makes the rename mean anything: `AppConfig.save()` raises `SettingsOverwriteRefused` and `write_run_record` WARNs + returns `False` when `paths.profile_superseded()` sees the breadcrumb (checked at the profile ROOT — the store sits under `runs/` on machine scope), because `load()` maps `FileNotFoundError` to defaults with no log and both writers recreate silently.

**The auto-grant window (amendment 3)** is PRE-SHELL (`ui_flet/grant_window.py` + the pure `grant_access.py`), rendered from `launcher.main`'s refusal path — the shell mount point does not exist at the moment of failure — branching on the TYPED reason (only `INACCESSIBLE` is grantable), re-execing on success, and saying UP FRONT that over-the-shoulder consent fails closed (the handshake is DPAPI CurrentUser → `DSYNC_DIFFERENT_ACCOUNT`).

## Honest predicates (S-2a)

**S-2a (honest predicates):** `shared_records: bool` is REQUIRED keyword-only on `probe_schedule`/`derive_schedule_status`/`sync_window_paused`, sourced from `is_machine_scope()` at all five view call sites, and the ONE rule everywhere is **suppress only when `foreign_account and not shared_records`** — Slice C (0046) made "the records land elsewhere" true by suppressing alarms; machine scope makes it FALSE. `FOREIGN_RECORDS_SHARED_NOTE` says records appear "from now on" (migration copies the ADMIN's `history.db`; the service account's own profile is never touched, so a pre-provisioning gap is real and permanent); `SYNC_WINDOW_SHARED_NOTE` makes a POSITIVE claim so it takes the schedule state and fires on CONFIRMED-LIVE only. `delivery_password_line` has four forms — form 2 (per-user) byte-identical, form 3's "no nightly is scheduled" on **MISSING only** (an UNKNOWN read-back is not an absence), form 1 with an account-less variant since `schedule_run_as_user` is `""` by contract when scheduling as the signed-in account. `home_status.machine_scope_line` is `None` on every per-user install (absent, not qualified) and `MACHINE_SCOPE_LINE_LEAD` + `diagnostics.SCOPE_SHARED`/`SCOPE_PER_USER` are single-sourced because the partner docs quote them to decide whether the manual `--sftp-configure` step is still needed — **and the wrong answer there is SILENT** (`tests/test_partner_doc_schedule_copy_parity.py` pins all three; three docs wrapped the phrase mid-line before the pin existed). `run_history.run_as_display` reduces the record's `run_as` to a bounded two-member vocabulary via `principal_key` — never a raw `DOMAIN\user` — and `components.run_table` renders the column only when values VARY (`""` is not a distinct value, so an upgraded ledger does not conjure it).

## The flow (S-2b)

**S-2b (the flow):** `RegisterBlock.DELIVERY_SECRET_UNREADABLE` is the ONE pre-UAC gate, ANDed with foreign-ness INSIDE `register_block` and read through `select_store()` (never "the keyring" by name — on a second provisioning the secret is already in the machine store); `FOLDER_NOT_SHAREABLE` is deliberately NOT a member (a confirm-level warning over `src/utils/unc.py` instead — the predicate is wrong in both directions and says so; DECISIONS 2026-09-18). `complete_handover` runs on EVERY outcome incl. a killed child, `persist` is bound to SUCCESS alone (a declined UAC must not record a nightly that does not exist), `refused` is TERMINAL and freezes Setup (the pin is left unset, so the next click can only crash), and switch-committed \u2227 register-failed LEADS with the scope change. `ui_flet/handover_result.py` is a process-scoped one-shot (`take()` reads AND clears) drained **once per Home mount, outside `_render`** and rendered ABOVE the verdict band — a deliberate one-paint exception to verdict-first. `setup_errors.classify_provision_step` is separate from `classify_schedule_error` because `ProvisionRefused.message` interpolates the step + icacls exit + a rollback clause and could never match an exact-equality branch; its completeness test closes a real hole, since the existing reflection sweep scans only `task_com`/`windows`/`elevated_apply`. `ReconcileOutcome.BLOCKED_DELIVERY_SECRET` exists because `BLOCKED_ACCOUNT`'s copy says "check the Windows account and its password" — a misdirect one field over from `BLOCKED`'s "fix the run time".

## The principal model (S-3) and gMSA (S-4)

**S-3 (the principal model):** `RegisterParams.kind: PrincipalKind` REPLACES the `password is not None` inference (deleted, not wrapped — `apply_definition` now has ONE `RegisterTaskDefinition` call and no branch); MSA uses `TASK_LOGON_PASSWORD`, **not** `TASK_LOGON_SERVICE_ACCOUNT` (with a domain `UserId` the `<LogonType>` element is silently dropped from the serialized XML), and `TASK_LOGON_S4U` stays undefined. Five states unrepresentable in `__post_init__`. `_do_register`'s ladder is kind-aware and `_do_provision` SHARES the callable — the make-or-break, because it validated unconditionally against a regex with no `$` and every foreign-principal register goes through elevation. `CronScheduler` refuses on the KIND (its old `password is not None` guard let an MSA through into a cron line with no account). `ScheduleReadback` gains `run_as`/`logon_type` for DISPLAY with a fail-open WARNING on mismatch; `foreign_task_account` still reads the RECORD.

**S-4 (gMSA, Settings only):** the disclosure sits behind `_build_schedule_section(allow_gmsa=False)` — the FIRST wizard/Settings fork in that function — and `schedule_run_as_kind` is the FOURTH atomic facet; `principal_kind_from_record` is the ONE spelling of the absent-value rule (stored wins, else `PASSWORD` iff a user is recorded) and can **never** return `MANAGED_SERVICE_ACCOUNT`, because sniffing the `$` off a name is the inference S-3 just deleted. BOTH gate rungs dispatch on kind (`ACCOUNT_SHAPE` ran `validate_run_as_user` unconditionally and refused every gMSA first, for the wrong reason). Errors FORK rather than multiply — no new canonical, since the gMSA taxonomy is unmeasured. **The "not yet tested against a live domain" hedging is GONE (owner decision 2026-09-21, reversing 2026-09-18's honesty constraint — shipping to SD60 as a supported option, and a second download just to delete a caption is partner friction).** `GMSA_UNTESTED_CAPTION` is deleted, not stubbed. What survived the removal is the OPERATIONAL content and is pinned: the MSA arm still shows `0x80070534` via `_code` and still offers NO "try again" (retrying a name the directory does not know changes nothing); `GMSA_PREREQUISITES` still renders on all three surfaces; and both partner docs + the CHANGELOG still state that provisioning runs BEFORE registration, so a failed gMSA register leaves the machine-scope switch COMMITTED and this version cannot undo it (`test_the_unshareable_consequence_survives_in_both_docs` replaced the retired hedge row — that consequence, not the hedge, is what a district cannot discover by trying). The failure taxonomy is still unmeasured, so a new gMSA failure gets a FORK + the `[HRESULT ` log anchor, never an invented canonical.

## The named hole

**THE NAMED HOLE:** `prune_principal` has a handler and an implementation but **no producer in `src/`** — Remove still sends only `{"op": "delete"}`, so a retired principal keeps its aces on the shared folder (ROADMAP; needs a decision on the unconfirmed-delete case).

## `--diagnose` — the support report (plan 0049 D7)

`python -m src.main --diagnose` prints the read-only support report (plan 0049 D7) — recognised in the **argv pre-check beside `--elevated-apply`**, because `_cli` pins the data dir and RETURNS a machine-scope refusal before argparse exists; it keeps ONLY the console attach from the preamble, guards every profile-resolving line on its own, and always exits 0. It carries no passwords but is **not PII-free** (Windows accounts, folders, the SFTP username) and its header says so.
