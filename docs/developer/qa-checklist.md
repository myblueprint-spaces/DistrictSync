# Pre-Release QA Checklist

A ~30-minute manual pass on the **built Windows exe** (not `python -m src.main`), run before every tag. These twenty-six checks are exactly what CI is structurally blind to: native file dialogs, real user-profile state, upgrade migration, and **whether the UI actually renders** (the pack smoke proves a window exists and closes — it asserts nothing about what is drawn in it).

> **Tip — keep it non-destructive:** set `DISTRICTSYNC_DATA_DIR` (an absolute path) to a throwaway folder before launching the exe and steps 2, 3, 4, 6 and 7 run against a scratch profile instead of your real one.
>
> **Note — the override does NOT cover steps 1 and 5.** While it is set, `user_data_dir()` resolves to it outright and `migrate_legacy_data_dir()` is a no-op — so step 1 would prove nothing about a genuinely fresh install, and step 5's restored profile would never be read. **Run steps 1 and 5 with `DISTRICTSYNC_DATA_DIR` unset**, moving the real profile aside as those steps say.

| # | Step | Expected |
|---|------|----------|
| 1 | **Fresh profile.** Move `%LOCALAPPDATA%\DistrictSync` and `~\.districtsync` aside, then launch. | The **launch page** opens first ("Who looks after this sync?"), NOT the wizard — no rail yet, no error banner. Past it you land on **Home**, and Home IS the wizard: one quiet line ("Welcome — this takes about 3 minutes.") above the District step with the "Choose your district" placeholder — and no step count in that line (the wizard's own "Step 1 of 5" indicator owns it). The rail highlight is on **Home**, and the **Setup item carries no attention dot**. Clicking Setup shows the same wizard at the same step (one wizard, two ways in) — but the band appears only on Home, by design. **Known, accepted:** type a path into the Folders step WITHOUT pressing Continue, then hop Home ↔ Setup — the typed text is gone. Each mount builds a fresh wizard, and only Continue persists a step; below the band the two surfaces are now the same wizard at the same step, so the hop reads like a no-op. Not a regression (it behaved this way before Home hosted the wizard). |
| 1a | **Launch page, happy path.** On a scratch profile (`DISTRICTSYNC_DATA_DIR`), type any local part at the real district domain **sd48.bc.ca** and press Continue. | It names SD48 – Sea to Sky ("That's … — you'll confirm it on the next step.") with "That's not my district" beside it. Get started opens the app. Re-launch: the launch page does NOT come back, and Settings' "Who looks after this sync" shows the address you typed. |
| 1b | **Launch page, typo + no-match.** Same scratch profile, cleared. Type `admin` (no @) and click away, then fix it to any address at **example.com** and Continue; then type `99` in the district-number box and click away; then press "That's not my address — try again". | The format error appears only AFTER you leave the field, never while typing, and never quotes what you typed. No-match reads calm and grey ("no problem"), never red, and says we don't have a **district** on file for that address — never "that address". SD99 says we don't have a mapping yet and points at support for a NEW mapping — it must NOT suggest choosing the closest district. "Try again" puts you back in the email field with your text intact. No dead end, no lock icon, no attempt counter, no spinner. |
| 1c | **The skip paths (both of them).** On a cleared scratch profile click "I'm not the person who looks after this sync"; then repeat, this time resolving a match and pressing "That's not my district". | Both open the app immediately, and `config.json` gains NO identity value either time (check the file) — a district you have just rejected is never stored. Re-launch: it asks again. |
| 1d | **Settings change + clear.** In Settings → Who looks after this sync: press Change, enter a different district's address, Save; then press Change again, blank the field, Save. **Then repeat the blank Save on a profile with NO address stored but a planted `config.corrupt-*.json`.** | The change names the new district inline. The blank Save reports EXACTLY what it did to the older `config.corrupt-*.json` copies — that it removed them, or how many it could not — and the folder agrees; `config.json`'s three `identity_*` values are empty/false. On the nothing-stored profile the planted copy must **SURVIVE** and the note must claim no deletion. |
| 1e | **Upgrade prompt, happy path.** On a scratch profile that is already SET UP (finish the wizard, or copy in a working `config.json`) with no address stored, open Home. Type an address at **sd48.bc.ca** — the district this profile is set up for — and press Save. | A small card sits UNDER the health verdict (never above it, and never between a fault and its fix button), with an OUTLINED Save. **Count the filled (solid blue) buttons on the whole screen: exactly ONE** — the verdict's fix CTA if there is a fault, otherwise "Convert now" in the quick-action strip. The card's Save is never the filled one. Saving names SD48 and says it matches what this sync is set up for. The card does not come back on the next launch, and Settings → Who looks after this sync shows the address. Nothing about the district, folders, schedule or delivery changes. |
| 1f | **Dismiss forever, then recover.** Same profile, cleared of its address. On Home press "Don't ask again"; re-launch; then go to Settings → Who looks after this sync, add an address, Save; then blank it and Save. | The card is replaced by one line saying we won't ask again and naming Settings as the way back. It never returns on re-launch. Settings still accepts an address afterwards, and blanking it re-arms the Home card on the next launch (this is the only route back). |
| 1g | **The mismatch card changes nothing.** On a profile set up for one district (e.g. SD48), answer the Home card with an address at a DIFFERENT district's domain (e.g. sd51.bc.ca). Press "Keep SD48 …" — **then clear the address in Settings → Who looks after this sync (blank the field, Save) and relaunch before repeating with "Change district"** (the card is one-time: without the clear it never comes back, and the second half would silently pass by not running). | It says you're set up for SD48 and your address matches SD51, that this can be perfectly normal, and that we've saved your address while your district and sync settings are unchanged. **Check `config.json` after each**: `sis_type` is unchanged both times, and the address you typed IS stored both times. "Change district" only takes you to Mapping — it switches nothing by itself. |
| 1h | **"We don't have a mapping for SD## yet".** On a fresh scratch profile, at the launch page enter an address at **example.com**, type `99` in the district-number box, press Get started, then finish the wizard so Home is reachable. On Home: press "Email support@…", then press "Don't show this again". | Home carries a second card headed "We don't have a mapping for SD99 yet" — it must NOT claim anyone is building one. The support address is readable and copyable on the card itself (so it still works with no mail client); the button opens a mail with a subject only, and **your own address appears nowhere in it**. Dismissing removes ONLY that card: the identity card's answer stays, `config.json` keeps `identity_email` and empties `identity_sd_number`, and any `config.corrupt-*.json` in the folder is untouched. |
| 1i | **A matched admin's lists are SHORT — and nothing is withheld.** On a fresh scratch profile, answer the launch page with an address at **sd48.bc.ca** and press Get started. Look at the wizard's District dropdown, finish the wizard, and check the same dropdown in Settings → Folders & district, plus Convert and Mapping. Then blank the address in **Settings → Who looks after this sync** and press Save, and look at all four again. | Every one of the four lists offers **only SD48 - Sea to Sky School District**, and the wizard's District step opens with it already selected. **No surface anywhere offers a "Show all districts" row** — it was retired on 2026-08-04, so a re-appearing row is the regression. With the address cleared, all four lists show **all eleven** districts again: that is the only escape, and it must work, or the scoping is a trap. |
| 1j | **The right district can never disappear.** On a profile **set up for a DIFFERENT district than your address** (e.g. `sis_type` = `sd74myedbc`, address at sd48.bc.ca), open Settings, Convert and Mapping. Separately, corrupt one district YAML in `config\mappings\` (add a stray `[`) and relaunch with an address at **that** district's domain. | First: every list carries BOTH SD48 and SD74 — the district your sync actually uses is never missing from the surface that edits it. Second: the broken district is still listed, nothing narrows at all (you see all eleven), and the log names the broken config **id** — never your email address or its domain. Restore the YAML afterwards. |
| 1k | **The welcome line knows an install that has been running.** On a scratch profile that HAS run before but never finished the wizard: finish setup **skipping the Schedule step** ("Set up later"), run Convert once, then edit `config.json` to `"setup_completed": false`. **If you did register a schedule, set `"schedule_registered": false` in the same edit** — the completion flag alone is re-inferred on load (`has_completed_setup()` is `setup_completed OR (complete config AND schedule_registered)`), so clearing only the flag lands you on the dashboard with no wizard and no welcome line at all. Launch and read the line above the wizard. | It reads "**Let's finish setting up — your files and run history are safe.**" and the word "Welcome" appears nowhere. The wizard resumes at the first step not truthfully done — not step 1 — and Run History still lists the earlier run. Nothing about the existing folders/district/schedule is cleared. |
| 1l | **The finish line is a save, and it is honest about failing.** Reach the finish step on a scratch profile. **First** make the profile folder read-only (Properties → Security → deny Write for your account) and press "Finish setup"; then restore write access and press it again. | The failed press **keeps the summary card exactly where it is** and adds "We couldn't save your settings just now — nothing was lost. Please try again." — it must NOT jump back to step 1, open Settings, or show the Home dashboard. The retry clears the note and lands you on **Home's health view** (not a Settings page). Check `config.json` after each: absent/unchanged after the failure, `"setup_completed": true` after the retry. |
| 1m | **The Setup tab's own wizard still graduates in place.** On a fresh scratch profile, click the **Setup** rail item (not Home), walk the wizard there and press "Finish setup". | The Setup surface turns into **Settings** in place with the one-time "Setup complete / You're all set — this is now your Settings page" band — it does not bounce you to Home. Then open Home: the health dashboard, no wizard. (Finishing from Home instead lands on Home's dashboard — both are correct; the difference is only where you pressed it. The two paths STILL differ in what they say at the finish line: the rail path confirms "Setup complete", the Home path hands you straight to the verdict. That asymmetry is a knowingly-open owner question, tracked in `docs/claugentic-ROADMAP.md` — it is not a defect to raise here.) |
| 1n | **The welcome line's THIRD variant: saved choices, no runs.** The abandoned-wizard state a real upgrader hits most. On a fresh scratch profile, past the launch page, pick a district and press Continue, fill both folders and press Continue — then close the app WITHOUT finishing. Re-launch (the launch page comes back only if you skipped it the first time) and read the line above the wizard. | It reads "**Let's finish setting up — everything you've already entered is safe.**" — "Welcome" appears nowhere (choices are on disk), and the words "run history" appear nowhere either, because this install has none and the line may only name what it can see. The wizard resumes at **Delivery**, not step 1, with your district and folders still filled in. |
| 1o | **A brand-new install is never told about "an earlier version" — and is never told about a nightly it doesn't have.** Three short passes. **(A)** FRESH scratch profile (delete the folder entirely — no `history.db`), finish the wizard from Home **skipping the Schedule step**; read Home, then Run History. **(B)** Another fresh profile, this time REGISTERING a schedule — read Home the moment you land, **then wait for the nightly-schedule card to appear** and read it again. **(C)** On profile (B), run Convert once, then delete only the ROWS from `history.db` (keep the file) and relaunch. | **Headline, every pass, both surfaces: "No runs recorded yet"** (except (C) — see below). It is a claim about the ledger, not the world: an install upgrading from v3.4.0 or earlier has no `history.db` either. **The two leads differ per surface by design** (Home speaks about the sync, Run History about the ledger beneath it) — do not report that as a defect. **(A)** the words "nightly sync" appear in NEITHER detail. **(B)** before the card resolves, Home reads "Your nightly sync will appear here." — **no time yet, and it must NOT say "your FIRST nightly sync"**; after the card appears it reads "Your nightly sync is scheduled for 3:00 AM." Run History names no time in either state. **(C)** both surfaces switch to "**Run history starts fresh here**" with the conditional "if you used an earlier version" line — and Run History's lead says "New **runs** will appear here", never "New nightly syncs". **NB — do not run (C) on the skipped-schedule profile (A):** once its probe confirms no task, BOTH surfaces switch to the "won't sync automatically" sentence and the "earlier version" line correctly disappears; that is not a defect. **The HEADLINE must agree across both surfaces in every pass** — that is the shared rule. |
| 2 | **Both Browse pickers.** Click Browse in the wizard Folders step AND on Convert (the v3.8.0 field bug). | Native dialog opens; the picked path shows in the field; the validation line updates. |
| 3 | **Convert fixture data.** Run Convert on `tests/snapshots/input` with the `sd74` config. | CSVs written; "Open folder" opens the output dir; Run History gains a `manual` row. |
| 3a | **Slim Home: the tiles are gone and the size number is not.** With the run from step 3 on record, open Home. | The verdict band is green, and its detail ends with one roster-size sentence beginning "**It included **" and naming students. There is **no tile row and no "LATEST ROSTER" label** anywhere on the surface. Below the verdict sits the quick-action strip: **"Convert now" FILLED**, "Run History" and "Settings" OUTLINED — exactly one filled button on the screen. All three buttons navigate, and the "will it run again?" nightly-schedule card (if you registered one) is still there below them. |
| 3b | **The size number never lies about a non-rostering district.** In Mapping switch to **SD51 - Boundary School District · Attendance** (if your list is scoped to one district, blank the address in Settings → Who looks after this sync and Save first), run Convert on an attendance extract, then open Home. Then, for the failure half, leave `sis_type` ALONE and instead break that district's own YAML in `config\mappings\` (add a stray `[`), and relaunch. | The healthy line counts **attendance rows**, not students — the words "0 students" must appear nowhere (the run record carries a zero for every entity that config does not emit, so this is the exact lie the check exists to catch). With the district's YAML unreadable the size sentence is **absent entirely** — never a guessed or zero number — and the rest of the verdict is unchanged. **Break the YAML rather than the `sis_type` value:** a bogus `sis_type` would suppress the sentence through TWO mechanisms at once (no entity list AND the run-from-another-district guard of row 3c), so its absence would prove nothing about either. Restore the YAML afterwards. |
| 3c | **RUN, THEN SWITCH — the number must not follow the new district.** The order is the whole point: row 3b walks switch→run→look, which can never catch this. With the SD51-Attendance run from 3b still the newest record, open **Mapping** and switch BACK to a rostering district (e.g. SD74 - Gold Trail); **do not run anything**; open Home. Then, for the mirror, switch to **myBlueprint+ (courses only)** and open Home again. | Both times the green verdict keeps its "Last sync delivered to SpacesEDU …" line and the roster-size sentence is **gone**: the counts came from one district and the entity list from another, so no number is printed. **"It included 0 students." / "It included 0 courses." must appear nowhere** — those were the two real renders this check exists to stop. (Switching a mapping does not re-register the nightly task, and Convert can run a district that was never saved, so this divergence is ordinary, not an abuse.) Now switch back to SD51-Attendance and re-open Home: the attendance number **returns** — the check suppresses a mismatch, it does not delete the feature. |
| 4 | **District coherence.** Change Convert's district dropdown away from the saved district (if your list is scoped to one district, blank the address in Settings → Who looks after this sync and Save first), then change it back. | Header chip stays on the SAVED district and the amber note appears (by design) — **and beside the chip an amber "This run: &lt;the district you just picked&gt;" pill appears with "Change mapping" next to it.** The pill names the PICKED district, not the saved one. "Change mapping" opens Mapping and switches nothing by itself. Changing back makes the pill disappear; Convert stays runnable throughout (the pill is a label, never a gate). |
| 5 | **Stale-profile upgrade.** Restore a previous release's profile (`config.json` with forward-slash paths), then launch. **Say which location you restored to — they test different things:** `~\.districtsync` exercises the legacy→platform **relocation** path (`migrate_legacy_data_dir` + the `MOVED.txt` breadcrumb), `%LOCALAPPDATA%\DistrictSync` exercises the old **config-format** path only (no migration). Walking both is ~1 extra minute. | Settings intact; Browse still opens; no crash. From `~\.districtsync`: the data appears under `%LOCALAPPDATA%\DistrictSync` and `MOVED.txt` is left behind. |
| 6 | **Exit + long path.** Quit the app and check Task Manager; also launch the exe from a deeply nested folder. | No `flet.exe` orphans; the deep-path launch behaves normally. |
| 7 | **Light-flavor exe renders** (the gate CI cannot be: it asserts a window EXISTS, never what is drawn). Open the built exe, walk one navigation (e.g. Home → Convert → Home), open the Schedule step's clock (`TimePicker`), and open one Browse dialog. | Every surface paints — text, icons, the navy rail; the TimePicker and the native Browse dialog both open and dismiss; nothing blank, garbled, or missing. |
| 7a | **The launch page paints** (it is now the FIRST thing a fresh install draws, and the pack smoke sees only that *a* window exists). On a fresh scratch profile, look at it before typing. | The gradient hero, the heading, the email field and the Continue button all paint; the field has focus; the escape link is visible. Close the window here with the title-bar X and check Task Manager: **no `flet.exe` orphans** (the close handlers are bound before this page, and it has no Exit button of its own). |
