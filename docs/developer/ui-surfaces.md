# Desktop UI surfaces

Developer reference for the native Flet desktop UI (`src/ui_flet/`): the shell and its load-bearing boot order, the launch page and the identity gate, every screen under `screens/`, Home's two branches, which modules are pure (counted) versus view glue, the settings model (`AppConfig`) with the identity modules it writes through, and the design-system summary. Moved **verbatim** from `CLAUDE.md` by plan 0053 S15 (2026-09-30) — headings and paragraph breaks added, no words changed (the change list is in `.claude/plans/0053-s15-disposition-map.md`). The rules stay in `CLAUDE.md` (**Subsystem guides → Desktop UI**). The authoritative design standard is [`docs/DESIGN_SYSTEM.md`](../DESIGN_SYSTEM.md) and the Flet API traps are in [`docs/FLET_1.0_CONVENTIONS.md`](../FLET_1.0_CONVENTIONS.md); the self-service creator is in [self-service-mappings.md](self-service-mappings.md), the Schedule section's principal model in [scheduler.md](scheduler.md), and what changes on a machine-scoped install in [machine-scope.md](machine-scope.md).

## The shell, the boot order and the gate

Native Flet 1.0 desktop app (no browser). `main.py`'s no-argv branch launches it via `src/ui_flet/launcher.py` (`boot_logging()` + one-time `migrate_legacy_data_dir()`) → `shell.py`.

**Boot order is enumerated in `shell.main`'s docstring and is load-bearing** (0038 S4a): chrome → geometry → close handlers (hoisted ABOVE the gate — the launch page has no rail and no Exit, so the title-bar close is its only exit) → `needs_identity` gate-or-`build_app_body(page, cfg)` → probes. `page.add(root_host)` runs exactly ONCE; the launch page and the app body swap via `root_host.content`; `_enter_app` is idempotent and re-loads `AppConfig` after the gate (persist-then-enter, so the first paint is correctly scoped).

**The gate is no longer one-way (QA 2026-08-18):** `_show_gate` is the ONE mount point (boot AND restart) and RE-ARMS the `entered` latch, so `on_restart_identity` — threaded `main` → `build_app_body` → Home's branch (a) only — can put the launch page back. The idempotency latch is therefore per-gate-cycle, not per-process; it still must come back up only on a SUCCESSFUL re-mount (a raise leaves content + latch untouched, so the floor is a genuine no-op). Any raise in the identity layer → log + enter unfiltered.

The app body = themed window + brand icon + left `NavigationRail` in ONE FIXED order (Home, Convert, Run History, Setup, Mapping, Help; D7) with rail-follow on programmatic nav + a schedule-attention Setup badge.

**Launch selection is Home in EVERY state since S6** (`nav.initial_destination_id`; `_INITIAL_WHEN_SETUP_NEEDED` retired and `NavModel` collapsed to `destinations` — `nav_model()` takes no config, so D7's "same rail in every state" is structural rather than coincidental), and the Setup badge is **suppressed while `nav.needs_setup`** (`needs_setup_badge(setup_unfinished=…)`) — an attention dot on the rail item whose wizard is on screen would flag the work in progress as a fault.

## The screens

Seven surfaces in `screens/`:

- `screens/identity.py` — **the launch page** (0038 S4a, LIVE): "who looks after this sync?" → one work email → EXACT public-domain match → matched-one (a correctable pre-selection) / matched-several / calm no-match (+ SD number → not-listed). The ONE `hero_gradient()` surface in the app (reallocated from onboarding) and — since 2026-08-04 — the ONE CENTRED one: `shell._gate_frame` centres a `GATE_WIDTH` column on both axes, the cards STRETCH to it, and the field carries no helper, no counter and no `max_length` (the length rule stays at the `validate_identity_email` boundary). Two 0.85.3 traps behind that, both in `docs/FLET_1.0_CONVENTIONS.md`: a scrollable `Column` silently ignores `horizontal_alignment`, and a blank `counter=` does not collapse the counter's band. Every path enters the app, incl. the text-tier escape ("I'm not the person who set this up" — stores nothing) and a crash. NO `ErrorCard` floor by design (it would be a dead end in front of the app; the shell's floor enters instead). The module docstring carries the "deliberately absent" list (no lockout / counter / delay / lock glyph / password field / network state) with reasons — read it before adding anything to this page. **`NOT_LISTED_NOTE_TAIL` is the SINGLE-SOURCE unmatched-district copy** (QA 2026-08-18): the launch page's no-match detail + unknown-SD note + not-listed note, Home's durable not-listed card and Settings' `IDENTITY_NO_MATCH_NOTE` all import it, because they previously gave three different answers to "so what happens now?". It points at the shipped default configurations and at `help.SUPPORT_EMAIL`; it never claims a mapping is being built. Wiring pinned by `tests/test_ui_flet_identity_page.py`.

- `screens/home.py` — **slim** health dashboard (0038 S7): one plain-language verdict ("did the roster sync?") whose HEALTHY detail carries ONE roster-size number + a quick-action strip + off-thread schedule read-back (D4), or — while `nav.needs_setup` — **Home HOSTS the setup wizard itself** (0038 S6, `_wizard_host`): `build_setup(page, on_schedule_changed=…, on_complete=…)` under ONE state-aware `home_status.welcome_band` line — **FOUR** variants, never "Welcome" over a year of records and never a step count (the wizard's own indicator owns that): fresh → `WELCOME_FRESH`; readable run history → `WELCOME_RESUME_WITH_HISTORY`; saved choices (alone, or beside a store that would not OPEN) → `WELCOME_RESUME_SETTINGS_ONLY`; **nothing saved AND an unreadable store** → the artefact-free `WELCOME_RESUME_PLAIN`. The rule is *never name an artefact you have checked is absent or cannot see*, and it binds the SETTINGS as tightly as the store — which is why the fourth exists. The three doc copies of these literals are tied back by `tests/test_ui_flet_band_copy_parity.py` (a fifth variant quoted in a doc without registering it there is RED). Behind a branch-(a)-SPECIFIC `ErrorCard` floor (the dashboard floor's "your nightly sync keeps running" is FALSE pre-setup; this one says nothing was changed + routes to Help). `on_complete` re-enters via `on_navigate("home")`, so the shell's fresh `AppConfig.load()` is what routes to the dashboard — it fires ONLY after a verified save, which is why a failed finish can't bounce anyone to step 1. `screens/onboarding.py` is RETIRED (the hero was a door into the room you were standing in).

  **S7 (slim Home):** the metric-tile row + its "Latest roster" label are GONE (`components.section_label` retired with them — Home was its only caller); the one thing they carried that the verdict does not — *does the roster look the right size?* — is now the healthy detail's `home_status.size_clause`, keyed on `mapping_catalog.active_output_entities(sis_type)` (ONE memoised config read per mount, never the eleven-YAML `catalog()` build — the S4b cost note still holds, pinned). The clause names whatever entity THIS config produces (students / attendance rows / courses) and **vanishes** rather than guess, because the run record writes every entity key with a defaulted `0` and cannot tell "not enabled" from "collapsed to zero" — a non-zero filter would have hidden the exact alarm. It ALSO vanishes when the counts record's own `sis_type` differs from the saved district (`size_clause(..., *, expected_sis_type)`, required kwarg, applied to what `_counts_source` RETURNS — the delivery walk-back can land on a third district): Mapping's Apply rewrites `sis_type` without re-registering the task and Convert can run a district it never saved, so the entity list and the counts legitimately diverge, and pairing them printed "It included 0 students." under a GREEN band. Beneath the verdict block sits `_quick_actions_row` (Convert / Run History / Settings, minus the destination the fix CTA owns); tiering is decided by the pure `home_status.quick_actions`, so **exactly one filled primary exists in EVERY dashboard state** (the healthy branch had zero before). Per-entity visibility moves to Run History one click away for the rostering + myBlueprint+ entities; an **attendance** district's row count reaches exactly ONE surface — that healthy size clause — since Run History's columns exclude `StudentAttendance`, and none at all on a warning/failed run (the clause is HEALTHY-branch only). An OPEN ROADMAP item, not a discharged residual.

  **Three identity cards (0038 S4b, LIVE)** ride the configured branch immediately under the verdict block — the anchor is deliberate (it survived S7's tile subtraction unchanged): (1) the one-time upgrade ask (`identity_gate.needs_identity_prompt` — readable ∧ setup finished ∧ not dismissed ∧ no usable stored address; never both asks from ONE settings state — the launch-page decliner stores nothing, so finishing setup legitimately re-asks once here, dismissible forever, tracked in ROADMAP), (2) the G3 mismatch card (session-local, only after a resolution whose match set EXCLUDES `sis_type`; Keep dismisses, "Change district"→Mapping; writes NOTHING either way; its detail names what WAS saved, since it renders after a successful write), (3) the durable not-listed card ("We don't have a mapping for SD## yet" — never a claim about vendor work nobody was told about; `unmapped_sd_number` over `available_configs()`, so it never builds the domain index; the `Email support@…` button + the selectable/copyable address beside it — `help.py`'s house pattern, because a bare mailto is a dead click on a locked-down server; dismiss clears `identity_sd_number` via `identity_save` — never `identity_clear`, whose quarantine purge is an erasure this is not). All writes route through `identity_save`, so no card can touch `sis_type`; card headlines are capped at the verdict's `type_section`/W_700 (type hierarchy IS verdict-first); the cards carry their OWN floor above Home's `ErrorCard` (an advisory bug may never replace the verdict). Copy is IMPORTED from the S4a constants wherever the fact is identical and written fresh where it differs (Home has no "next step" and nothing pending to "choose") — the shared headline is why "is the launch page showing?" is now asserted structurally (no rail + the launch-page-only escape label), not by that string.

- `screens/setup.py` — **"Who looks after this sync" leads the Settings scroll** (0038 S4a): the stored address shown plainly (only after `stored_identity_email` re-validates it), Change re-runs the SAME resolution inline, **blank CLEARS** via `identity_clear` (both fields + `identity_prompt_dismissed` reset; the `config.corrupt-*.json` copies swept only when something WAS stored, and `identity_cleared_note` branches on the real outcome so a failed unlink is never reported as a deletion). Adds no filled primary and no reconcile — identity is not a task-baked arg.

  Also: **first-run 5-step WIZARD** (District → Folders → Delivery → Schedule → honest adaptive finish; District leads per 2026-07-15 user decision, Delivery still precedes Schedule so `--sftp` is baked before registration); Schedule + Delivery are skippable. Run time uses a `ft.TimePicker` clock affordance (the TextField stays the value source of truth). Once completed, graduates to a flat **Settings** scroll (rail label stays "Setup") ordered folders/district → schedule → delivery + ONE reconciling Save (re-registers when any task-arg changed).

  **S6:** `build_setup` takes `on_complete` — the HOST seam. `_finish` is save-THEN-verify: a raised `cfg.save()` rolls `setup_completed` back on the instance, keeps the finish summary on screen with `FINISH_SAVE_FAILED_NOTE` (retry = press again), logs WARN, and does NOT fire `on_complete`; with `on_complete=None` (the Setup RAIL item) the SUCCESS path is unchanged (the in-place `_mount_settings(transition_cue=True)` graduation) while the FAILURE path is deliberately NEW on BOTH mounts — a raised save used to escape uncaught. Pinned by a text/label equality test over the two mounts, because a rail item and a hosted wizard that diverge are two wizards. Schedule → per-op UAC-elevated `register_task`; SFTP → side-effect-free test + keyring-on-Save-only.

  **The Schedule step has TWO transient ADVANCE-only gates** (`FlowInputs.window_valid` + `schedule_busy`; neither reaches `derive_flow`, so neither moves resume/satisfaction): an enabled-but-invalid seasonal window, and a register/unregister IN FLIGHT (QA 2026-08-18 — Continue used to abandon a registration mid-UAC). `on_busy` is raised/lowered in the SAME places the section toggles its own buttons, and `_dispatch` lowers it if the handoff itself raises, so the gate can't outlive what it gates.

  **`schedule_skipped` is no longer write-once:** a CONFIRMED-LIVE read-back clears it (only LIVE — UNKNOWN/MISSING leave the defer standing), because a latched defer made the finish line report "not scheduled" against a task that WAS live. Neither password persisted to `AppConfig`. Only the wizard finish line flips `setup_completed`.

  **S5:** both district dropdowns (wizard step + Settings folders card) are `filtered_catalog`-scoped — **unconditionally since 2026-08-04**, when the owner retired the `list_scope_row` show-all row from all four pickers (the escape moved to the INPUT: blanking the stored address in this same scroll widens every list); the wizard's auto-select seed reads the VISIBLE list and is applied **AFTER** `derive_flow` — order is load-bearing, since seeding it first marks the District step satisfied and resumes PAST the step the launch page just promised.

  **The seed fires ONLY when nothing is saved** (a resumed wizard with a district already set skips the step entirely, as it always has), and when it fires the step's caption SAYS SO (`district_auto_seeded_note`) instead of instructing a pick already made — a pre-selection nobody is told about is a silent default.

  **Service account (0046 B):** the static "This task will run as: X" caption is now an editable `SCHEDULE_ACCOUNT_FIELD_LABEL` field PREFILLED from `cfg.schedule_run_as_user or _keyring_owner_account()`, and the typed value is sent to `register_task` VERBATIM (stripped only) — `setup_gates.principal_key` decides GATES and NOTES, never what to SEND (INVARIANTS). `_account_facts` is the ONE assembly point (its `force_blank_password` blanks the PASSWORD only — never the account); `_paint_account_note` repaints the gate's REASON under the field at build time and on every keystroke, so a disabled primary always has a visible cause, and carries the `--sftp-configure` delivery note when delivery is ON and a service account is in play on either side. `_keyring_owner_account` (renamed from `_run_as_account` FIRST, alone) still names the KEYRING OWNER in the delivery line and must never be repointed at the principal. `_apply_result`'s banner names `sent_account`, both classifier sites pass the REAL `account_is_current` (0047's `False` arm is live at last) and so does `_apply_unregister`, read from the RECORD before the clear. A raised `ValueError` from `validate_run_as_user` gets `_WORKER_ERROR_ACCOUNT_SHAPE`, never the transient generic. The reconcile refuses an in-place principal switch (`BLOCKED_ACCOUNT_SWITCH`) and routes to Remove → Schedule — the field keeps what was typed.

- `screens/convert.py` — run a conversion now on a worker thread (`job_runner.py`); explicit district (no `configs[0]` fallback, no input-dir fallback — fails loud on unset output); anomaly-ack write-gate; resolved-output caption + "Open folder"; optional SFTP delivery; writes a `source="manual"` run record. **S5:** the district dropdown is `filtered_catalog`-scoped (the prefill membership test moved to the VISIBLE ids — safe because the saved district always rides the list; no show-all row since 2026-08-04) and the header gained a `this_run_label` "This run: <district>" pill + "Change mapping" that appear on DIVERGENCE only — a label, never a gate (`can_run_convert` untouched).
- `screens/run_history.py` — read-only past runs from the SQLite run store (`src/history/store.py`), NOT log parsing; plain-language status (no raw error/path column); honest fresh-start empty state after this update. **Its empty-state RULE and both headlines are imported from `home_status` (S7)** — `has_earlier_run_history(store_created_at=…)` alone, never `has_completed_setup()` (the wizard flips that on save, which told every brand-new install about "an earlier version" it never had). The stamp cannot separate "never ran" from "ran before `history.db` existed" (shipped v3.5.0, no backfill), so `EMPTY_NO_RUNS_HEADLINE` claims only the LEDGER ("No runs recorded yet") and no empty-state sentence on either surface NAMES a nightly without a positive signal — Home gates its nightly-naming leads on `home_status._expects_a_nightly` (confirmed-LIVE read-back OR `schedule_registered`, and its lead says "your nightly sync", never "your FIRST": that gate admits the ≤v3.4.0 upgrader by design); **BOTH** of this banner's leads simply name none (the upgrade arm is gated on the store stamp ALONE, so a manual-only install reaches it — it says "New **runs** will appear here"), and the nightly is named only by the confirmed-LIVE append. Both leads are pinned by exact-string rows in `tests/test_ui_flet_run_history.py` — they were referenced nowhere until the S7 discharge round, so either could revert green. The LEAD sentences stay per-surface by design; the parity sweep asserts VERDICTS on the record axis and headline equality only on the empty state — `tests/test_ui_flet_home_history_parity.py`.
**Home's branch (a) also carries the ONE way back to the launch page** (`RESTART_IDENTITY_LABEL`, QA 2026-08-18): text-tier, beside the welcome band, wired only when the shell passes `on_restart_identity` (absent ⇒ no affordance, never a dead one). It writes through `identity_save(identity_email="", identity_sd_number="")` — **never `identity_clear`**, whose quarantine purge is an erasure a mistyped address is not (same distinction the not-listed card's dismiss makes) — and clears BEFORE re-mounting, since `needs_identity` reads the stored address; a refused write keeps the admin put behind `setup.IDENTITY_REFUSED_NOTE`.
- `screens/mapping.py` — review the active district config and switch to another pre-built one (NOT a YAML editor — the full editor is a ROADMAP item). **S5:** ONE `filtered_catalog` build per mount (the old double `list_configs()` parse is gone); the current mapping is always offerable, so a switch is always revertible. Since 2026-08-04 there is NO show-all row, so a matched admin switches only between their own district's tiers.
- `screens/help.py` — links out to the SpacesEDU Help Centre + support email; plus the read-only "who looks after this sync" echo (0038 S4a — rendered ONLY when the stored address re-validates; carries "we don't send it anywhere" because `about.support_mailto` stays subject-only — flag 6) + a one-click hop to Settings.

## Pure (counted) logic versus view glue

Pure COUNTED (tested) logic: `tokens`/`theme`/`verdict`/`nav`/`humanize`/`home_status`/`schedule_status`/`schedule_probe`/`convert_result`/`convert_output`/`failure_copy`/`run_history`/`mapping_catalog`/`identity_gate`/`config_editor`/`preflight` (the last is `src/etl/preflight.py`, not a `ui_flet` module)/`setup_errors`/`setup_gates`/`sftp_copy`/`setup_flow`/`job_runner` (the retired `run_log` parser is replaced by the `history.store` reader); view glue (`shell`/`nav_rail`/`components`/`picker_field`/`launcher` + `screens/*`, incl. `screens/identity.py` and `screens/creator.py`) is coverage-omitted (`screens/onboarding.py` left the omit list with the module — S6). Build all controls via `components.py` (see `docs/FLET_1.0_CONVENTIONS.md` — e.g. `ft.Dropdown` uses `on_select`, `ft.FilledButton` uses `content=`; the wrong forms raise `TypeError` on 0.85.3).

## The settings model and the identity modules

- `src/config/app_config.py` — Runtime config (`config.json` in `paths.user_data_dir()`); SFTP non-sensitive settings + `setup_completed`. `has_completed_setup()` (D4a) is the SINGLE durable finish-line (explicit flag OR `is_complete() and schedule_registered`, baked on load so no deployed install regresses into onboarding); `sis_type` defaults to `""` (D9 — no silent district). Unix file permissions (0o700/0o600).

  **`schedule_run_as_user` (0046 B)** is the THIRD atomic facet beside `schedule_unattended`/`schedule_task_args` — written only on a confirmed register, cleared on a confirmed unregister, in the SAME save; `""` = the signed-in account, which is EVIDENCED (every build before it passed `run_as_user=None`). Its `schedule_` prefix is a NAMING CONTRACT: it keeps the field OUT of `_ADVISORY_FIELD_PREFIXES`, so `_carries_chosen_settings` counts it. NEVER a password — a NAME only.

  **Identity (0038):** `identity_email`/`identity_prompt_dismissed`/`identity_sd_number` — the `identity_` prefix is LOAD-BEARING (it puts them in `_ADVISORY_FIELD_PREFIXES` alongside `window_`, so an identity-only save on an UNREADABLE profile is refused by the existing `_carries_chosen_settings` machinery). `identity_save(**updates)` is **the ONE sanctioned identity write path** (review-maintained — nothing mechanically prevents a direct attribute write + `save()`): re-checks `settings_unreadable()` at WRITE time, validates KEY *and* VALUE before applying any of them (membership in the dataclass-derived `_IDENTITY_FIELD_NAMES`, never `hasattr` — which would let `identity_save=...` shadow the method — plus `_value_fits`, because a mis-typed value makes the whole `config.json` UNREADABLE on next load), refuses any non-`identity_*` key loudly (so it can never rewrite `sis_type`), swallows+logs `SettingsOverwriteRefused`/`OSError`, ROLLS THE INSTANCE BACK (the AppConfig is SHARED across every Settings section — a refused write left applied would render state the disk lacks and get committed by the next unrelated Save) and returns a bool (advisory data must never trap the admin).

  `identity_clear()` (0038 S4a) is the ERASURE path → `ClearOutcome(cleared, removed, remaining)`: routes through `identity_save` (blanks both fields + resets `identity_prompt_dismissed` so the ask can return), then unlinks the `config.corrupt-*.json` siblings — gated on BOTH a confirmed write AND `had_identity` read BEFORE it (a blank Save on an install with nothing stored must not destroy the settings-recovery copies of the very population most likely to own them). `remaining` exists so the note can't claim a deletion that failed; a stranded `.config.json.*.tmp` is a named residual no sweep reaches.
- `src/utils/identity.py` — COUNTED identity primitives (0038): `normalize_email` (trim→lowercase→NFC; plus-addressing KEPT, exactly ONE trailing root dot stripped) + `extract_domain` (after the FINAL `@`). **No salt/hash/scheme** — matching compares PUBLIC district domains. Posture inversion vs `ALLOWED_SFTP_HOSTS`: same normalize-then-compare shape, OPPOSITE failure mode — TOTAL and must never narrow to zero (consumers fail OPEN). Boundary validation is `validators.validate_identity_email` (returns the value UN-normalised; its messages never echo the address). Domain matching is EXACT string equality — never subdomain/suffix.
- `src/ui_flet/identity_gate.py` — COUNTED pure gate + matching (no flet, no I/O). `needs_identity(cfg)` = readable settings ∧ setup unfinished ∧ no USABLE stored identity (mirrors `nav.needs_setup`); `stored_identity_email(cfg)` re-validates the stored value at READ time (`config.json` is hand-editable and the load check is TYPE-only — a failure means UNANSWERED, never echo it); `stored_identity_domain(cfg)` (S5) is the ONE reduction every filtered picker consumes — `""` when unusable **or** when `settings_unreadable()` (that state has no trustworthy identity AND no saved district to fall back on, so it must not narrow anything); `gate_reason` (bounded PII-free log word); `can_continue`; and `resolve_domain`/`matched_state`/`resolve_sd_number` — EXACT case-normalised domain equality, never subdomain/suffix (over-matching is the dangerous direction under fail-open); the index is taken as DATA, which is why S5 could swap its source without touching the resolver. S4b adds the three Home-card rules: `needs_identity_prompt` (the same ask on a CONFIGURED install — the ONE input it adds is `identity_prompt_dismissed`; swept as mutually exclusive with `needs_identity`), `matched_excludes_saved` (G3 — deliberately narrow: no match and no configured district are both non-questions, never a disagreement) and `unmapped_sd_number` (total over a hand-edited value; a number we DO ship returns `""`, so we never claim to be "building" a mapping that is in the exe). LIVE since S4a: `shell.main` gates on it, `screens/identity.py` resolves through it, `screens/home.py` cards read it. It can only ask a question — it can never withhold anything and must never fail closed. Since S5 the effectful side is ONE session-memoised `mapping_catalog.catalog()` build, projected as `district_domain_index` (identity surfaces) or consumed by `filtered_catalog` (the four pickers).

## The design system

**Design system — `docs/DESIGN_SYSTEM.md` (authoritative) + the `districtsync-design` skill:** "Branded Professional" (Direction B). `tokens.py` = the ONLY hex/size source (`space_*`/`radius_*`/`type_*` scales + Direction B roles: navy rail, `color_content_wash`, toned status tints + deep on-tint text — all AA-gated in `UI_CONTRAST_PAIRS`); `components.py` = the ONLY control factories (`page_header`/`HealthVerdictBanner` verdict band/`metric_tile`/3-tier buttons [primary filled · secondary OUTLINED · text]/`card`/`district_chip`/`status_pill`). Rules: build via factories (never inline hex/size in screens), ONE filled primary per screen, verdict-first layout, toned bands not saturated fills. Skill triggers on any `src/ui_flet` change.
