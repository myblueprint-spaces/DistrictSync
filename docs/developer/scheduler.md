# Scheduling: the task, its principal, elevation and the seasonal window

Developer reference for `src/scheduler/` — the in-process COM task (`windows.py` + `task_com.py`), the declared principal model, the `_fail` log line and the HRESULT-keyed failure classifier, per-operation elevation and the cron adapter — plus the principal's pure half in `setup_gates`/`setup_flow` (plan 0046 B) and the seasonal sync window (`src/etl/sync_window.py`), which pauses the scheduled run in the app rather than in the OS. Moved **verbatim** from `CLAUDE.md` by plan 0053 S15 (2026-09-30) — headings and paragraph breaks added, no words changed (the change list is in `.claude/plans/0053-s15-disposition-map.md` (deleted in DSYNC-18; in git history)). The rules stay in `CLAUDE.md` (**Subsystem guides → Scheduler**). Where the scheduled run's profile and secrets live on a machine-scoped install, and how provisioning shares the elevated child, is [machine-scope.md](machine-scope.md).

## The Windows scheduled task

- `src/scheduler/windows.py` — **In-process COM end to end since plan 0041 S1a+S1b** — `register_task` / `read_schedule` / `delete_task` all drive `src/scheduler/task_com.py` (lazy pywin32, dynamic Dispatch only [`gencache` AST-banned], bounded daemon workers 10s/30s/120s; live-probed traps: the real HRESULT hides in `excepinfo[5]`, the COM never-run null-date is **1999-11-30** not 1899, pywin32 stamps local wall-clock `+00:00` so tzinfo is stripped): **zero child processes** — `powershell.exe` AND `schtasks.exe` both left the `system_binary` allowlist (icacls remains, in `elevation.py`).

  **The principal is DECLARED, not inferred (plan 0049 S-3):** `register_task` takes a `task_com.Principal(kind, user, password)` — required, undefaulted, one object through the `Scheduler` Protocol and both adapters — and `apply_definition`'s `password is not None` inference is DELETED (one `RegisterTaskDefinition` call site, AST-pinned; the logon comes from `logon_type_for(kind)` and the RunLevel from `honours_run_highest(kind)`). Three `PrincipalKind`s: `PASSWORD` → `TASK_LOGON_PASSWORD` + RunLevel per `run_highest` (an in-process BSTR to `RegisterTaskDefinition` — never argv, never any env, never logged, never in the returned message); `INTERACTIVE_TOKEN` → interactive token + **always** Limited, `run_highest` ignored; `MANAGED_SERVICE_ACCOUNT` (S-3, reachable from NO UI until S-4) → **`TASK_LOGON_PASSWORD` with a NULL password**, never `TASK_LOGON_SERVICE_ACCOUNT` (5) — MEASURED: with a domain `UserId` that value makes Windows silently DROP `<LogonType>` from the serialized XML, so the constant is not even defined here (nor is `TASK_LOGON_S4U`). Five unrepresentable states are REFUSED in `__post_init__`, never defaulted (PASSWORD without a password · MSA with one · INTERACTIVE_TOKEN with one · an MSA name without `$` · a PASSWORD name with `$`), and the **request/command asymmetry is deliberate**: `Principal` ALLOWS an interactive-token request naming a foreign account so the boundary can answer it with `_MSG_ACCOUNT_NEEDS_PASSWORD` (a constructor `ValueError` would replace that sentence with a traceback), while `RegisterParams` — the COMMAND, built from an unsealed request file in the elevated child too — carries the fifth refusal. `task_com.validate_principal_account(kind, user)` is the ONE kind→validator dispatch (4 call sites, 2 processes): `validators.validate_gmsa_account` for an MSA (a SHAPE check and its docstring says so; refuses BY NAME, in both halves, `<COMPUTERNAME>$` — a computer account has the gMSA shape and is SYSTEM-equivalent — and any `NT AUTHORITY`/`BUILTIN`/well-known form), else the UNCHANGED `validate_run_as_user` (still rejects `$`). The elevation predicate is the KIND (`kind is not INTERACTIVE_TOKEN and not is_elevated()`) — keying on the password would have sent a passwordless MSA down the direct path to a certain access-denied — and `CronScheduler.register` refuses on the KIND too (its old `run_as_password is not None` guard let an MSA through into a cron line that silently dropped the account). Failure messages are the **HRESULT-keyed, injective, marker-guarded** `task_com.MSG_*` canonicals (INVARIANTS — `MSG_NOT_FOUND` owns the "cannot find" idempotency marker, `MSG_ACCESS_DENIED` the elevated-retry one; an unmapped code carries Windows' own description **plus its hex status**, and `format_hresult`/`hresult_for` are the ONE code↔message spelling), OR this module's own `_MSG_*` elevation categories, OR a `DSYNC_`-stripped child message off the elevated path.

  **Every literal `return False, …` outside `_fail` is AST-banned** (an indirect tuple return is review-upheld, not mechanically pinned), so every direct `(False, msg)` return goes through `_fail(…, *, verb)` → one `_FAIL_LOG_FORMAT` line `Failed to <verb> task '<name>': <msg> [HRESULT 0x… | n/a]` (ERROR; WARNING on the two `_confirm_*` unconfirmed arms, both of which take a required `path_label` so a direct-path timeout never claims elevation; silent ONLY for an already-absent task on remove; the optional `detail` suffix carries `type(exc).__name__` on the two generic arms, where a non-COM exception has no code to recover), so a district's log has one grep anchor. `is_elevated()` (win32 `IsUserAnAdmin`, else False) feeds `setup_errors.classify_schedule_error(msg, elevated, *, account_is_current)` — the COUNTED pure classifier, which IMPORTS the `task_com.MSG_*` + `windows._MSG_*` canonicals and keys on them by EXACT equality (cause-first copy, each HRESULT branch showing its code via `hresult_for`), keeping ONE `ACCESS_DENIED_MARKERS` substring floor that shows NO code and tells an un-elevated access-denied (→ run-as-admin) from an elevated one. `account_is_current` is REQUIRED and undefaulted (it selects personal-credential coaching, wrong for a service account); a UAC-approved CHILD refusal arrives as its own `_MSG_ELEVATED_ACCESS_DENIED` canonical, because the `elevated` flag is the PARENT's token. The task action injects `--source scheduled` (env `DSYNC_SOURCE` fallback); a non-elevated `register_task` / `delete_task_elevated` self-elevates per-operation via `src/scheduler/elevation.py` (the app itself never runs elevated) with DistrictSync itself as the dispatch-first `--elevated-apply` child (`src/scheduler/elevated_apply.py` — no `_cli` preamble side effects run elevated; fail-closed ladder; a refused request READ **or** a cross-SID DPAPI failure → the `DSYNC_DIFFERENT_ACCOUNT` sentinel, mapped on BOTH ops; SAME `task_com` functions as the direct path = structural single source). `query_task` is RETIRED — schedule truth is `read_schedule() -> ScheduleReadback` (tri-state LIVE/MISSING/UNKNOWN, owned by the pure `ui_flet/schedule_status.py`). Since S-3 `TaskFacts`/`ScheduleReadback` also carry `run_as` + `logon_type` off `Definition.Principal` (read by the extracted, MagicMock-testable `task_com.task_facts`, which owns its OWN `finally` re-bind — a caller's cannot release another frame's COM locals) — **DISPLAY only**: the one consumer is `_warn_on_principal_mismatch`, a logged WARNING that FAILS OPEN and names no account, and `schedule_probe.foreign_task_account` deliberately keeps reading the RECORD (a live read that legitimately answers `None` must not switch a suppression on and off). Inputs validated via `validators.py` at BOTH halves; `current_run_as_user()` returns `DOMAIN\user`

## Run-time failures: the task fires but DistrictSync never starts (DSYNC-32)

A registration that succeeds is not a nightly that runs. Several prerequisites — the 'Log on as a batch job' right, a gMSA's password-retrieval permission, the principal's read/execute on the exe and its folder — are checked by Windows only when the task FIRES, so the failure never reaches `_fail` or `setup_errors`: DistrictSync never started, wrote no run record and no log line. The only evidence is the task's own `LastTaskResult`, read back by `read_schedule` and classified by `ui_flet/schedule_status.run_result_verdict` — a channel deliberately separate from the registration classifier (the `RESULT_*` constants in `task_com.py` share numbers with some `HR_*` ones and are distinct names on purpose). The verdict is computed FIRST in `_live_status`: `SCHED_S_TASK_RUNNING` (`0x00041301`) is never a fired-but-no-record contradiction (LastRunTime moves at the start, the record lands at the end); a reported failure heads the contradiction copy with its `0x%08X` code; the "moved or deleted" remedy needs positive evidence from `schedule_probe.registered_program_moved` (the read-back's `action_path` missing, or — frozen — not `Path(sys.executable).resolve()`, case-insensitive on Windows). The probe's WARNING carries the code and verdict name, never an account or a path. Home's band and Run History's banner offer the log folder (on a machine-scoped install `runs\`, one `etl_tool-<account>.log` per account) and a bounded copy of the task name / last run / result / next run. Task Scheduler's own history is off by default; the partner guide `docs/partner/managed-service-accounts.md` says how to enable it.

## The schedule check: proving the nightly can start (DSYNC-33)

The run-time failures above are found at 3 AM; for a managed service account they are now looked for at scheduling time. `src/scheduler/schedule_check.py` owns it, and it rides the **provision** op's existing elevated child — the gMSA path always provisions (a gMSA is never the signed-in account), so there is ONE UAC prompt for register + check. The parent asks for it with the REQUIRED `build_provision_payload(..., schedule_check=)` key; the child (`elevated_apply._schedule_check`) runs it only when `schedule_check.requested(payload)` — the key is literally `True` AND `applies_to(kind)`, which is MANAGED_SERVICE_ACCOUNT only (a password principal rides the identical code path; it was left out on purpose — its registration already validates the credential, and every existing service-account district would gain up to a minute per Schedule press). An older parent's payload has no key and gets no check.

**Before the prompt** `provision_session.request_provision` resolves a gMSA through `provisioning.account_sid` (the existing `LookupAccountNameW` wrapper, now raising `AccountLookupError(winerror)`): `ERROR_NONE_MAPPED` (1332) → `ProvisionOutcome.ACCOUNT_NOT_FOUND`, anything else → `ACCOUNT_LOOKUP_FAILED` — the second is never worded as a typo, because a domain controller out of reach is not one. Nothing is sealed and no prompt is shown; the log line names the outcome and the Win32 code, never the account.

**In the child, after the nightly registered** (`schedule_check.run_for_payload`, total — never raises): the nightly's `RegisterParams` are rebuilt from the payload through the same validators, two ADVISORY facts are read, each on a `task_com.bounded` worker capped at `ADVISORY_CALL_TIMEOUT_S` = 10 s and UNKNOWN when it runs out (both can reach a domain controller) (`batch_right_state`: the account's DIRECT `SeBatchLogonRight` / `SeDenyBatchLogonRight` via `LsaEnumerateAccountRights`; `install_state`: `NetQueryServiceAccount`, where only `MsaInfoInstalled`/`CanInstall`/`CannotInstall` are mapped and every error or other answer is UNKNOWN — an API that could not answer is never a finding), then `run_check`: look `<task_name>_Check` up FIRST — a task by that name whose action carries `--schedule-check` is our own leftover from a killed child and is deleted before registering (so its stale `LastTaskResult` is gone); ANY other task by that name (or a lookup that cannot answer) is somebody else's, is never registered over (`TASK_CREATE_OR_UPDATE` would) and never deleted by the `finally`, and the check reports `CHECK_NOT_REGISTERED` (inconclusive) — then register `<task_name>_Check` through `task_com.apply_check_definition` — the SAME `_new_definition` + `_register_definition` the nightly uses (the module's ONE `RegisterTaskDefinition` call, AST-pinned module-wide), so principal, password, program, start-in folder and run level are identical and only the arguments (`--schedule-check <32-hex token>`, with the same `windows.module_prefix`), the name and the trigger differ — `IRegisteredTask.Run`, poll `State` + `LastTaskResult` + `LastRunTime` every 2 s (≤5 s per sample) for at most `POLL_TIMEOUT_S` = 60 s (clock and sleep injected), read the marker, classify. A sample counts only once the task was seen queued/running after our `Run` or its `LastRunTime` is at or after the `Run` call (whole seconds) — a result from before ours is never read as this check's. Classification keys on the same `task_com.RESULT_*` constants as `schedule_status.run_result_verdict` (a parity test pins the two together) plus the hidden mode's own exit codes; the success exit counts only with a marker carrying THIS token (`MARKER_MISSING` otherwise — an exit code alone is never proof). `TIMEOUT`, `CHECK_NOT_REGISTERED`, `CHECK_NOT_STARTED` and `UNAVAILABLE` are INCONCLUSIVE and never worded as a finding.

**The hidden mode** (`DistrictSync --schedule-check <token>`, `schedule_check.run_check_mode`) is recognised in `main._cli`'s argv pre-check beside `--elevated-apply`/`--diagnose`, above the preamble. Running AS the account, it pins the data dir exactly as a real nightly does and exits 81 (marker written), 82 (pin refused — `MachineScopeRefused` or an unusable dir), 83 (pinned, but not to the shared folder), 84 (`runs\` refused the marker) or 85 (bad token) — distinct from the real run's 0–3 and from every `RESULT_*`. It writes ONE file, `runs\schedule-check-<token>.json` (token, sanitised account, timestamp, version — bytes, atomic), and reaches no ETL, delivery, run store, config, migration, console or log sink (pinned by tripwires with a live twin).

**One deadline.** All of `run_check` lives inside `CHECK_DEADLINE_S` = 90 s from its first clock read: every COM call is bounded by `min(15 s, time left before the delete reserve)` and none starts without time to finish, the poll stops before a sleep plus a full sample would cross that line, and `DELETE_RESERVE_S` = 15 s is held back so the `finally`'s delete always gets its full bound. `TOTAL_BUDGET_S` = 2 × 10 s advisory + 90 s = 110 s is what the child can spend after the nightly registered, and `windows._ELEV_TIMEOUT_S` = `_ELEV_PROVISION_BUDGET_S` (120 s — the provision op alone, what the wait used to be) + 110 s + `_ELEV_MARGIN_S` (20 s) = 250 s, the arithmetic in a comment and the inequality pinned by a test — because a child the parent KILLS runs no `finally` and a successful provision would read UNCONFIRMED.

**Cleanup guarantees.** `run_check`'s `finally` deletes the check task (only once the name is OURS — never a foreign task's) and the marker on every path, each best-effort on its own, including a raise inside the poll. Two backstops cover a child that is KILLED (no `finally` runs): the check task's one trigger starts in the past (it never fires; `StartWhenAvailable` is False) and ends 15 minutes ahead, with `DeleteExpiredTaskAfter = PT0S`, so Task Scheduler removes it after expiry (documented behaviour, unmeasured here); and the next check sweeps `schedule-check-*` files older than an hour (prefix-scoped) — only after the shared folder passes `paths.assert_machine_dir_trusted`, because the sweep runs ELEVATED in a folder the service account can write; an untrusted folder skips the sweep, never the check.

**The channel back is bounded**: `ScheduleCheck.to_wire()` is `{verdict, code, batch_right, installed}` — three enum values and one int — added to the result file only when a check ran (every other result keeps its exact shape). The parent re-validates it with `from_wire` (an unknown value is UNAVAILABLE/UNKNOWN, a non-uint32 code is dropped), logs ONE line (`provision_session.CHECK_LOG_FORMAT`: verdict NAME, `format_hresult` code, the two advisory values — INFO when it passed, WARNING otherwise; no account, no path) and carries it on `ProvisionAttempt.check` → `HandoverResult.check` (required keyword on `handed_over`) → `setup.handover_banner(result, *, page, task_name)`, which paints `schedule_check_band` under the handover band on Home (re-entry lands there) or in Setup's slot when nothing rebuilt. Every word is `ui_flet/schedule_check_copy.py`'s (pure, counted): HEALTHY confirmation; FAILED finding with the note, the code, the hints only a DEFINITE advisory answer earns, the prerequisites pointer (Windows-side failures only) and the retry hint; WARNING when inconclusive. The non-passing bands carry the DSYNC-32 log actions, text tier.

**The nightly is NOT rolled back on a failed check** (DECISIONS 2026-10-23). The verdict is reported; the task stays registered. A rollback would turn an advisory, possibly-inconclusive probe into a gate that deletes a working schedule (a slow first start, a timed-out poll), and the machine-scope switch it shipped beside cannot be undone anyway — so the admin would be left with a committed shared folder and no nightly, the one state the handover copy exists to avoid.

**Remove revokes a gMSA's folder access** (`provision_session.request_removal_with_revoke`, the first producer of the `prune_principal` op): for a recorded MANAGED_SERVICE_ACCOUNT principal on a machine-scoped install, Setup's Remove sends `{op: prune_principal, task_name, user, kind}` instead of the plain delete — ONE prompt; the child deletes, confirms MISSING by read-back and only then prunes. The parent confirms the removal itself (`windows._confirm_removal`, never the child's `ok`); a `prune` failure is "removed, access kept"; a `delete` failure is resolved by read-back and prunes nothing; a refusal BEFORE the delete (an unresolvable account, an untrusted/overridden profile, a malformed request, a handshake that could not be built) is `RevokeOutcome.FALL_BACK` and Setup removes the nightly the ordinary way — a revoke that cannot run must never be why a nightly cannot be removed. A password principal is still removed with the plain delete.

## Elevation and the cron adapter

- `src/scheduler/elevation.py` — Windows per-operation elevation IPC primitive (D5): `ShellExecuteExW("runas")` on the absolute System32 `powershell.exe` (bounded wait, never INFINITE), DPAPI CurrentUser inbound password blob (fail-closed on SID mismatch — never LocalMachine), plaintext atomic result (no secret), orphan-handshake sweep. Consumed by `windows.py`.

## The scheduled-task principal — the pure half (plan 0046 B)

**The scheduled-task PRINCIPAL (0046 B, pure half).** `setup_gates.principal_key` is the ONE reduction every principal comparison goes through (`""` = the signed-in account; blank ≡ current and case-insensitive, restating `windows.register_task`'s own equivalence) and `register_block(config_complete, run_time, *, account: ScheduleAccountFacts)` is the gate WITH its reason — ordering config → run time → principal, shape checked ONLY for a FOREIGN account (G5: a legitimate `PC\John Smith` prefill must keep registering), and `ACCOUNT_SWITCH_NEEDS_REMOVE` fired whenever a live task's principal is not PROVABLY the requested one (`recorded is None` included — an unproven record cannot authorise an in-place re-point). All the new keywords are REQUIRED and undefaulted, deliberately: this plan exists because one defaulted parameter substituted a security principal. `setup_flow` gains the principal as `RegisteredSchedule`'s THIRD facet (never `TaskArgs` — "fields baked into the ACTION", and its persisted shape rides 20 installs), a principal clause in `schedule_reconcile`, the SERVICE-ACCOUNT `downgrade_interrupt` variant (it names the account and overrides `keep_next_*` too, because "your Windows account password" is the wrong credential; `offers_signed_in_only=False` since the gate would make that button dead) and `BLOCKED_ACCOUNT`/`BLOCKED_ACCOUNT_SWITCH` beside the untouched `BLOCKED`, whose copy hardcodes "fix the run time". `task_com.MSG_ACCOUNT_NOT_RECOGNIZED` / `HR_NONE_MAPPED` (`0x80070534`, MEASURED on our COM path and DISTINCT from a wrong password) and `windows._MSG_ACCOUNT_NEEDS_PASSWORD` both get `setup_errors` branches — the second left 0047's `DELIBERATELY_UNCLASSIFIED` set here, which is what the produced-vs-classified sweep forced.

## The seasonal sync window

- `src/etl/sync_window.py` — **Seasonal sync window** (v3.8.0): pure `today`-injected `in_sync_window(today, start_md, end_md)` (MM-DD bounds, wrap-around Aug→Jul, boundary-inclusive, leap-safe via `(month, day)` tuple compare — never builds a date, so `02-29` can't raise) + `next_resume_date`. The window lives in the APP, NOT the OS schedule: the task stays a plain daily trigger and `main._cli` skips a run whose resolved source is `scheduled` when the window is enabled and today is outside it (exit **0** — a paused night is healthy, not a failure; no ETL/write/delivery, no run record). So it recurs yearly with **nothing to re-arm** — no scheduler change, no elevation. Opt-in (`AppConfig.sync_window_enabled` default off → year-round, byte-identical). Manual Convert / hand-run CLI / headless cron BYPASS. A malformed enabled window fails LOUD and runs (never silently stops the sync). **Fields are named `sync_window_*` deliberately — `window_*` is the geometry-exclusion prefix in `app_config._carries_chosen_settings`.** The paused fact is single-sourced at `ui_flet/home_status.sync_window_paused` and read by Home, the Run History banner AND the Setup nav badge so they cannot disagree; a confirmed-MISSING schedule OUTRANKS the pause (a gone task won't resume, so "resumes <date>" would be a lie).
