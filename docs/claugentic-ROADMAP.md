## What this app is & does  _(generated by /claugentic-dev-harness:audit · do not edit — re-run to refresh)_

<!-- harness-audit:overview:start -->
_Inferred from project structure, manifests, and docs — not from running the app. Refreshed 2026-09-03._

**What it is** — DistrictSync is a desktop/server **data-conversion tool** for school districts (British Columbia today, other partners planned). It takes the raw student-information exports a district pulls from MyEducation BC and reshapes them into the CSV files SpacesEDU / myBlueprint+ need for rosters, classes, and course history. It ships as a single double-clickable program (built with PyInstaller) so non-technical district staff can run it on a school server — usually on an automatic nightly schedule set up by the built-in first-run wizard.

**What it does** — It reads a district's export files, cleans and reorganizes them, and writes up to eight output spreadsheets (students, staff, families, classes, enrollments, two optional course-catalog files, and an optional attendance feed). It can preview changes without writing, compare against the previous run, produce a data-quality report, and deliver the finished files to SpacesEDU automatically over a secure (SFTP) connection with the server's identity pinned in advance. Twenty bundled per-district/tier configuration files handle each district's quirks (file names, columns, email formats, calendar dates) without code changes — and, new since the last audit, a district admin can now **author their own district mapping in-app** (a thin overlay YAML written to the user profile, test-converted, then activated) without waiting for a vendor release.

**How it's built** — Python 3.13, using pandas for the data work and pydantic to validate configuration. It's a classic ETL pipeline: **Extract** (read the export files) → **Transform** (one focused transformer per output type) → **Load** (atomic CSV writes). A native desktop app (Flet) provides the first-run setup wizard, a health dashboard, manual conversion, run history backed by a small local database, and the self-service mapping creator; Windows/Linux scheduling helpers automate the nightly run (Windows scheduling is in-process COM with per-operation elevation, so the app itself never runs as administrator).

**How it's organized** — The code lives under `src/` (~92 modules): the pipeline stages in `src/etl/` (one focused transformer per output type under `transformers/`, plus a pure pre-flight column-check), configuration handling and the new self-service authoring in `src/config/`, secure file delivery in `src/sftp/`, scheduling in `src/scheduler/`, run history in `src/history/`, shared safety/validation utilities in `src/utils/`, and the native UI in `src/ui_flet/` (pure tested logic kept separate from coverage-omitted view glue). Every district's mapping rules are plain YAML files in `config/mappings/`.

**Safety-net signals** — Strong. A large automated test suite (~3,900 test functions across ~125 files) with an 80%-coverage gate, a "golden file" regression test pinning one district's exact output bytes, an output-schema contract test across every bundled config, configuration validation for all 20 configs, and a full three-OS continuous-integration pipeline (lint, formatting, type-checking, a security scan, and the tests) plus pre-commit hooks (an email-leak scanner and an architecture-tree freshness gate). The codebase documents explicit guarantees: atomic writes with rollback, "no orphan" roster integrity, fail-loud error handling, a fixed exit-code contract, and a privacy split that keeps student data out of logs.

**Confidence & caveats** — High confidence in the structural picture: this is a mature, well-documented, unusually disciplined project. Because this overview is read from the code's structure (not from running the tool against real data), the audit that follows focuses on where the *standards* — especially **student-data privacy, data integrity, and reliable delivery** — could still be strengthened, with fresh attention on the newest surface: the self-service mapping creator, which lets an admin's own YAML enter a pipeline that carries student PII.

**[MACOS SMOKE, observed 2026-09-01 in run 33526796672] Launching the `.app` from a mounted DMG leaves ONE orphaned `flet` view process at teardown; the bare binary left zero.** Directly comparable evidence, same runner OS, one variable changed: the v3.13.0 macOS job (bare binary) logged `close: new-view orphans after teardown: []`, and the first mounted-`.app` job logged `[3073]`. **Not established:** whether this touches a real user at all. **[AV / DISTRIBUTION] The Windows exe trips heuristic antivirus, and a quarantined Flet client bricks the window permanently.** Observed live on 2026-08-04: Bitdefender ATC blocked `DistrictSync-windows.exe`, and what it actually removed was `%USERPROFILE%\.flet\client\flet-desktop-full-0.85.3\flet\flet.exe` — every DLL and `data\` left in place. `flet_desktop.ensure_client_cached()` returns early whenever the cache DIRECTORY exists without checking the executable inside it, so every later launch resolves a path that is no longer there and dies with `FileNotFoundError [WinError 2]` in `create_subprocess_exec`. Deleting `%USERPROFILE%\.flet\client\` fixes it (the client re-extracts from the embedded `flet-windows.zip`, offline) — **confirmed by the owner on their own machine**, which is why nothing ships for it in v3.10.0. Four candidate fixes, roughly in value order: **(1) code-sign the exe** — Azure Trusted Signing (~$10/mo, org needs 3+ years of history) or an OV/EV certificate; behavioural detection is not silenced by a signature, but the unsigned-unknown-publisher multiplier is, and district IT will ask for it regardless; **(2) stop shipping one-file** — `--onedir` plus an installer removes BOTH the self-extract-to-`%TEMP%` pattern and the drop-and-execute of a second unsigned exe into the user profile, which is the most malware-shaped thing the product does and happens on first launch, before any scheduling; **(3) drop `powershell.exe -EncodedCommand`** from `src/scheduler/windows.py` — base64 PowerShell is explicitly weighted by ATC, Defender ASR and most EDR; the Task Scheduler COM API (`win32com`) spawns no child process at all, and `schtasks /XML` is the boring fallback (see that module's docstring for why it was left); **(4) report the false positive** to Bitdefender and Microsoft, and check VirusTotal for breadth. **Owner call, 2026-08-04 (recorded so it is not silently re-litigated):** the self-heal was DEFERRED, not rejected — the concern was launch-time cost. For whoever picks it up: the cheap form is one `os.path.isfile` on `<cache>\flet\flet.exe` before `ft.run` (a single stat, microseconds — it does not enumerate or hash anything), and only a MISSING exe triggers the rmtree-and-re-extract. Delete-and-re-extract on EVERY launch is the expensive shape the owner was right to reject: ~96 MB of I/O and a second or two added to every start.
