## Problem

Four owner-approved gaps (Brief 0037, Phase 1):

1. **The exe ships ~100MB of Flutter client it doesn't need.** The `full` desktop flavor is embedded on Windows/macOS (`.github/workflows/flet-pack.yml:30,46`) though the app uses no audio/video; Linux already ships `light` (PLAT-0b). D-0037-1 flips Win/mac to `light`. A standing decision (DECISIONS 2026-07-14) declined this pending "a green Win+mac UI smoke"; the pack smoke is the closest existing instrument — it gates offline-embed on all three OSes and window-exists + zero-orphan close on Windows (macOS close is INFO-only), and it asserts no rendered content. **It has never run on `light` for Windows or macOS** — the flip PR's own CI run produces that evidence, and the pre-tag QA-checklist walk on the built exe (required by D-0037-6) is the rendered-content gate. Expected saving: the 2026-07-14 entry measured the full client at 99.8MB and estimated 30–45MB; the size-echo step settles the real number.
2. **The new-user front door is a door into a room you're standing in.** Unconfigured Home renders an onboarding hero whose CTA routes to the Setup rail item (`src/ui_flet/screens/home.py:285-290` → `onboarding.py`). D-0037-2: Home hosts the wizard itself. Post-setup, Home is a metric-tile dashboard (`home.py:207-209`) whose tiles lose their counts on any imperfect run (ROADMAP L59); D-0037-3: slim Home = one verdict line + quick actions.
3. **The app doesn't know who it's talking to.** All 11 district configs are offered to every admin in three pickers; the highest-consequence wrong click in the product is picking the wrong district (a wrong mapping ships a wrong roster — student PII). Two of the eleven rows render byte-identically today ("SD51 - Boundary School District" twice — `sd51attendance_mapping.yaml` inherits SD51's `district_name`; verified). D-0037-4: a launch identity page resolves the admin's work email against per-district salted-hash contact lists baked in the bundled YAMLs and scopes every district list; labels become distinguishable.
4. **The output contract lives nowhere.** No doc lists the emitted CSV columns; `tests/test_contract.py:35-57` asserts membership (not order), covers 5 of 8 entities, and asserts nothing about the per-entity BOM rule (`loader.py:53`). Brief item 4: an in-repo `docs/developer/output-contract.md` + strengthened tests.

Plus the P1 leftovers: the Convert header chip asserts the *saved* district while the run uses the *picked* one (`convert.py:1166-1173` — the code comment admits it); no CI job runs the built exe's CLI branch at all (and `flet-verify.yml`'s path filter excludes `config/**`, so config PRs never build an exe); QA-checklist and product-spec rows for every new surface.

## Goals / Non-goals

- **Goal:** an existing configured install upgrades onto slim Home with a one-time, non-blocking identity prompt — never a launch gate. The three upgrade shapes are named and each has a pinned landing: complete+registered → slim Home + identity card; complete+manual-only → Home hosts the wizard **with a state-aware band** ("finish setting up", never "Welcome") because `has_completed_setup()` is honestly False for it; UNREADABLE → slim Home, no gate, no card (G2).

Banned vocabulary (in-app copy, docs, release notes): sign in / log in / verify / unlock / authorized / account / credentials / access — and the contact list is never described as protected / secured / anonymous / not harvestable / encrypted.
- **Non-goal:** real contact-list VALUES. Hash lists ship EMPTY until the pre-release owner approval (framed as per-row publication consent); the hashing tool + schema land now. **The unclaimed-config rule (below) makes "empty lists = today's district lists" structurally true**, not incidentally true. (The launch identity surface and slim Home are visible changes in their own right — the "behaves like today" claim is scoped to the district pickers.)
- **Non-goal:** changing the CLI. `src/main.py::_cli` is untouched by identity (G1); pinned by an import-graph test (`main.py`'s reachable imports never include the identity module) — a bounded regression guard, plus the exe smokes.

## Approach

### Identity = one pure primitives module + one additive config key + one launch page that can never trap anyone

- **Primitives** (`src/utils/identity.py`, COUNTED): `normalize_email` (lowercase/trim; NFC; plus-addressing and trailing-dot handling decided once and pinned), `hash_email` (SHA-256 over `SALT + normalized`, hex-truncated to 48 bits, scheme `v1`), `validate_identity_email` lives in `validators.py` (allowlist charset, exactly one `@`, ≤254 chars, reject CR/LF/control chars) and runs at the boundary before normalize/hash/persist. The salt is a **committed constant** with a docstring stating: not a secret, intentionally public, never move to keyring/env (baked hashes must be reproducible), defends against casual scraping only. A pinned known-answer vector makes any salt/scheme drift fail a gate loudly. The module docstring names the posture inversion vs `ALLOWED_SFTP_HOSTS`: same normalize-then-compare shape, **opposite failure mode** — this filter must never raise and never narrow to zero (`test_unknown_email_enters_unfiltered`).
- **Config key:** `MappingConfig.district_contact_hashes: list[str] = []` — top-level next to `district_name` (`models.py:579`). `model_config = ConfigDict(extra="ignore")` is **declared explicitly** with a forward-compat rationale comment (today it holds only by Pydantic default while five sibling models declare `forbid`). A field validator pins each entry to `^[0-9a-f]{12}$` lowercase — a plaintext address pasted into the list fails `make validate-config` loudly, in CI, before it can ship. A one-line test asserts `to_raw_dict()` output is unchanged by the key's presence (top-level fields structurally cannot reach the ETL — the test converts that from observation to gate). Tests pin: the `myedbc` base never carries hashes (a base hash would leak to **every descendant config**), and every config whose resolved list is non-empty contains the owner's hash (vacuous during dev, live at the pre-release bake — guards `_deep_merge`'s wholesale-list-replacement on any child that restates the key). **No config `version:` bump** — the loader's "bump MINOR on new features" docstring (`loader.py:43-49`) is amended to scope the gate to ETL-affecting keys, recorded as a dated DECISIONS entry (a bump would also be noise: half the bundled configs pin their own `version` and resolve to 1.0).
- **Owner tool:** `scripts/hash_district_contacts.py` — **imports** `identity.normalize_email`/`hash_email`/`SALT` (never re-implements; the tool and runtime are one versioned scheme), reads a LOCAL plaintext candidates file (path argument; refuses any input path under the repo root), emits complete per-config `district_contact_hashes:` blocks (always including the owner row), prints only `sis_type → hash` + masked local parts (`j***@sd40.bc.ca`), writes nothing (the owner pastes), fails loud on an unparseable row, and carries `--verify <candidates> <config-dir>` reporting "N of M candidates resolve to their intended district" — the pre-release drift check. Unit-tested (the `test_ci_flet_pack_smoke.py` precedent) including a plaintext→script→YAML→match round-trip.
- **Repo hygiene gate:** an email-shaped-regex scan joins the existing pre-commit hook and CI, over the **whole repo** (tracked files) with a short explicit allowlist (`help.py`'s `SUPPORT_EMAIL`, the `example.com/org/invalid` synthetics) — a future legitimate address is a visible allowlist line, never an invisible path hole; `.gitignore` gains `*allowlist*candidate*` / `*.emails`. Plan/spec/QA files are public surfaces under the same rule.
- **The launch page** mounts in `shell.main` between the geometry block and the app body. The refactor is honest about its size: the window-close lifecycle (`page.window.on_event` AND `page.on_disconnect` — the zero-orphan guarantees, today at `shell.py:417-434`) hoists ABOVE the gate; `page.add(root_host)` happens once, with the identity view and the app body swapped via `root_host.content` (the proven `content_host` pattern — no new 0.85.3 API); the app body extracts to a module-level `build_app_body(page, app_cfg)` (not a 110-line closure); the Setup badge probe stays after entry. Boot order is enumerated in the spec and pinned: close handlers bound while the page is up; `_enter_app` runs exactly once; closing at the identity page orphans nothing (title-bar close accepted — no rail, no Exit button, stated).
- **The page can never trap anyone:** `needs_identity(cfg)` (pure: not `settings_unreadable()`, not `has_completed_setup()`, no stored `identity_email`) + **a floor over the whole identity layer** — any exception in the predicate, the render, or resolution logs and falls through to the app body (`_enter_app()`), making "never fails closed" mechanical, pinned by a smoke that injects a raise into the identity build and asserts the shell mounts. **Persist best-effort, then enter — never trapped, never mis-scoped:** resolution attempts the wrapped persist FIRST (`SettingsOverwriteRefused`, `OSError` → log + continue; the gate re-asks next launch), then calls `_enter_app()` with a **fresh `AppConfig.load()`** so the first session's lists are correctly scoped from the first paint; a persist failure still enters (never a trap). The order joins the boot-order enumeration, and a first-paint test pins that the app body sees the persisted identity. All identity writes route through one `identity_save()` choke point that re-checks `settings_unreadable()` on the instance it is about to save (the guard lives on the WRITE, not the boot-time decision). Structurally: the new fields are all `identity_*`-prefixed and join an `_ADVISORY_FIELD_PREFIXES = ("window_", "identity_")` exclusion in `_carries_chosen_settings`, so an identity-only save on an unreadable profile is refused by the existing machinery.
- **Page states** (all local — resolution never touches the network; no spinner, no fake latency): initial (field focused, Continue gated) · invalid format (on blur/submit, never while typing) · **matched-one = a correctable pre-selection** ("We'll show you SD48 – Sea to Sky School District's settings." / "Not your district? Choose a different one." — never "We found your district", never "You're authorized") · **matched-several** (the owner/support guaranteed path: "Which district are you setting up?" + short list) · no-match (calm, no red: "We don't have that address on file yet — no problem." → type SD number, or "My district isn't listed yet") · SD-number resolves / doesn't ("We don't have a mapping for SD## yet" → not-listed path) · not-listed (enter on unfiltered defaults; persists `identity_sd_number`) · **escape** ("I'm not the person who set this up" — enter unfiltered, store nothing, re-ask next launch) · fail-open (unreadable contact lists → enter unfiltered, silent to the admin, one WARN in the log naming the config id). A **"deliberately absent"** list rides the spec: no lockout, no attempt counter, no artificial delay, no lock glyph, no password field, no network/connecting state — each absence is the register.
- **Identity logging** (ops trace, PII-free — counts only; the address, its hash, hash prefix, domain, and local part are ALL banned, a hash being trivially reversible at this population size): `identity gate: shown=<bool> reason=<...>` and `identity resolve: outcome=<matched|no_match|invalid|show_all> matched_districts=<n> configs_with_contact_lists=<n>/<total>`. INFO for normal empty/no-match; WARN only for a config the filter consulted that failed to load.
- **Existing installs** (`has_completed_setup()` true): never the launch page. A dismissible identity card on Home, attached immediately after the `HealthVerdictBanner` append (a position that survives S7's tile subtraction — the S4/S7 seam is explicit). Card states: idle / invalid / matched / **matched-but-differs-from-configured** ("You're set up for SD48 – Sea to Sky, and your address is on file for SD51 – Boundary." / "That can be perfectly normal. Nothing has been changed." → [Keep SD48] dismisses · "Change district" → Mapping, which owns the stale-schedule honesty of a switch) / matched-several / no-match / dismissed (permanent — `identity_prompt_dismissed`; lives on in Settings). **Resolution never rewrites `sis_type`; changing the identity in Settings never changes `sis_type`.**
- **Settings section** "Who looks after this sync" (top of the Settings scroll): the stored address shown plainly, Change re-runs the same resolution inline, blank **clears** (`identity_email` + `identity_sd_number`; clearing also resets `identity_prompt_dismissed` so the states can't wedge — pinned), the per-session show-all affordance beside it. Saves ride the Settings scroll's existing ONE reconciling Save. Help echoes the stored address read-only with a link to Settings ("who looks after this sync" — it does NOT promise the address is used in support mail, because it isn't; flag 6).
- **`identity_sd_number`'s reader** (it earns persistence): the durable not-listed card on Home — "We're building the mapping for SD##" + "Email support with a sample extract" (prefilled support path) — shown while `identity_sd_number` is set with no matching config. Phase 2 swaps the button for "Build my mapping".

### Filtering = one catalog-layer choke point with an unclaimed-config rule

- **The rule (the design's load-bearing correction):** a config is hidden **only when its resolved `district_contact_hashes` is non-empty AND does not contain your hash**. Empty, absent, or unresolvable (degraded `loaded_ok=False`) lists mean *unclaimed* → **always shown**. This makes fail-open per-config, not just global: SD54/SD74 (contacts uncollected at launch) can never vanish from a matched admin's list; a degraded config stays listed (Apply already disables); a user-dropped YAML that omits the key can't erase its own district. A district *disappearing* is strictly worse than no filtering, and it's exactly what a hashing mistake would otherwise produce silently under fail-open.
- **Placement:** matching + the display rules live at the **catalog layer** (`mapping_catalog.filtered_catalog(email_hash, *, saved_sis, show_all, config_dir=None)`) — `identity.py` stays primitives-only; the plaintext email is confined to the identity/Settings screens + AppConfig. **Data source specified:** `ConfigSummary` gains `contact_hashes: tuple[str, ...] | None` resolved during the same single catalog build (no re-parse; the memoization survives) — `None` = unresolvable/degraded, `()` = declared-empty, and only a **non-empty** tuple can ever exclude (the unclaimed rule distinguishes all three). The module's no-PII docstring is re-worded honestly: student-PII-free as ever, but it now deliberately carries pseudonymous contact-hash data — the module's ONE identity-adjacent fact (the `run_history` "ONE deliberate identity fact" precedent). Layer note vs CLAUDE.md's UI/ETL isolation: the matching rule sits in this UI-layer module deliberately — it is presentation scoping (which rows a picker shows), it consumes config data the module already loads, and the ETL structurally cannot see the key (`to_raw_dict`). `saved_sis` is a signature parameter unconditionally included in the result — the escape is a property of the choke point for every caller that passes it (the three call sites each pass `app_config.sis_type`; a truth-table row pins it). Deterministic ordering pinned. Consumed by `setup._district_options()`, **`setup.py:350`'s auto-select seed (the previously-unnamed fourth consumer)**, `convert.build_convert`, and `mapping.build_mapping` — one catalog build per mount, passed down (mapping.py's current double `list_configs()` parse collapses to one), memoized per session so the launch path never re-parses 11 YAMLs per paint; any raise in catalog building degrades to unfiltered.
- **D9 interaction decided:** the wizard's District seed reads the same filtered list; `auto_selected_district` under a filtered one-entry list now auto-selects the matched district — aligned with D9's "auto-select only when exactly one option exists", now scoped to the *visible* list, correctable at the District step (which is a pre-selection surface by design). The stale DECISIONS L120 "unreachable branch" note is updated in the same slice.
- **Labels:** the sd51 collision dies via the one-line `district_name` (flag 10) — every `friendly_district_name` consumer (11 sites incl. the mismatch note, Run History's "Different district", Help, the support subject) inherits it. The picker-row builder disambiguates deterministically on any residual display-text collision (appends the sis id) — covering user-dir YAMLs we don't control; the G13 test pins the **bundled** catalog renders no two identical labels and is written first and observed RED on current main (the collision is real today).
- **Show-all:** a text-tier row at the foot of each filtered list, rendered ONLY when a filter is actually applied; wording "Show all districts — we're only showing yours to keep the list short"; when on, the row inverts to "Showing all districts · Show only mine". Per-session (flag 5).

### Contract = a doc with per-row provenance + assertion strengthening (zero runtime change)

- **`docs/developer/output-contract.md`:** front-matter (`contract_version` semver · `emitted_by: DistrictSync >= vX.Y` · `published_reference: Advanced CSV v1.0 (2025-07-23)` · changelog table) and a **Trust chain** section: live importer (external, unversioned, source of truth) → this doc (maintained mirror, per-row dated confirmations) → `test_contract.py` (mechanical enforcement of the mirror) — our tests guard our side of the handshake only; a named re-confirmation trigger (any change to a base field_map key set/order, `_NO_BOM_ENTITIES`, or the attendance knobs requires fresh importer confirmation before merge). **Confirmation is per row, never doc-wide:** rows the owner confirmed 2026-07-27 (`EnrollStatus`/`SchoolCode`) carry that stamp; unconfirmed rows (the CourseInfo/StudentCourses header-spelling variants, the attendance vocabulary/date format) are marked *pending owner confirmation* with the reconciliation question.
